# Parallel Scenario Evaluation

Functional cases run independently and may overlap. File ordering is not an
execution dependency. Use this guide for prerequisites, ownership and release
checks; see [fixture contracts](evaluation-fixtures.md) for sandbox injection.

## Environment and ownership

Use the platform's dedicated test-account credential chain. Live cases currently
select `cn-hangzhou`; change the region consistently if the dedicated account's
fixtures are elsewhere. Query the actual account ID and available IDaaS instances.
Select a suitable instance deterministically from the returned list; do not guess
IDs or accept missing M2M/PAM entitlements as a successful test. The account-mode
cases need an existing test IDaaS instance with available M2M quota; the
specific-instance case also needs at least one ECS in the same account and region.
The PAM success cases need PAM enabled. These are shared prerequisites, not
resources created or deleted by the suite.

Each case generates its own session ID and resource-name prefix. Record successful
creation IDs immediately. A resource prepared by a case belongs to that case;
a resource that predates it does not. For application reuse and name conflicts,
prepare the application or conflicting provider inside the same case. Never rely
on another case's creation, names, exports, or completion.

Before the first write on a selected instance, independently call GetInstance
with its actual ID to confirm it remains accessible and record DefaultEndpoint.
The earlier list response does not replace this pre-write readback.

Parallel cases can temporarily fill a shared instance's provider quota. A list
count alone does not establish the quota limit: require an actual quota rejection.
After reconciling and cleaning its own partial preparation, a case may poll the
full provider lists every 30 seconds for at most 600 seconds. Retry preparation
only after an observed count decrease makes room; the conflict scenario needs two
slots. Limit provider preparation writes to eight per case. Do not repeat a
license-denied candidate or an ambiguous write, and never free another case's
resources. Expired waiting without capacity remains an environment failure.

Clean up only recorded creations with explicit test teardown authorization.
Disable before deleting. A refusal must first leave the resource unchanged;
`cleanup-declined` obtains a separate, explicit teardown authorization afterward.
If interrupted, use the recorded IDs to resume cleanup; never delete by a broad
name prefix or by enumerating all resources in the test account.

## Cases and coverage

There are 23 standalone scenarios: 18 functional and 5 routing. `autoGenerated`
and `userDefined` record provenance; both use the same offline quality checks.
Keep each JSONC self-contained for platform execution. Do not add duplicate
scenarios to inflate counts or share created resources between cases.

The validated maintenance baseline is `898d11399c8436815bb6af3accbfa3911b947bb6`:
Run 33527 / request 15228 passed 26/26 Skill cases and 190/190 assertions with
Forbidden 0. Coverage report 11740 passed capability 100%, information 2/2,
error types 4/4 and positive Trigger. Platform assertion coverage was **N/A**
(suggestion generation 1/6); this is separate from executed assertions passing.
Skipped classifications and baseline-control failures are not functional passes.
These are historical results, not evidence for a later modified package.

The current candidate consolidates three former controls: standalone identity
joins the empty-list scenario; RPC and plugin ECS reads share one sequential
scenario; selected-instance readback is already covered by the richer POP
inventory with same-instance/provider bindings. Existing UUIDs and all seven
mock-case registrations remain stable. The four injected error categories,
five routing cases and all lifecycle branches remain separate.

Long lifecycle prompts are written once in execution order, with one
candidate/ownership/quota policy per case. The four error prompts retain the
validated baseline wording after Run 33550 reported fault-recognition failures;
the actual responses and preserved-diagnostics checks passed, but that does not
make the fault-recognition assertions pass. The Token prompt explicitly requires
actual HTTP_STATUS, error and error_description in the final answer, matching
the existing response assertion without relaxing it. JSONC files remain self-contained;

## Execution and evidence contracts

- Keep the installed Skill, certificates and CLI unchanged during a run. Fix
  the repository before evaluating a new snapshot; do not repair code in a sandbox.
- Python process assertions use `method: skill_script` plus `script_path`;
  direct CLI assertions use `method: aliyun_cli`. Use the published
  [scenario schema](https://code.alibaba-inc.com/alicloud-skills/skill-testcase-gen/blob/master/references/schemas.md).
  Positional script arguments are not `--key` flags. CLI patterns use plugin
  spelling; PascalCase in permission/API declarations names RPC Actions.
- Export actual IDs as `${params.*}`, consume them only after their producer,
  and bind readback/teardown to those IDs. Successful creation requires its
  returned-ID stdout marker; application creation also requires
  `M2M_STATUS=enabled`. An early APP_ID is still recorded for failed-setup cleanup.
- PAM-positive cases independently GetInstance and check PAM=enabled on the
  final candidate **before** resource creation. Actual authorization must return
  `PAM_AUTH=auto_done`; disabled modules use the separate non-PAM branch.
- Mutating scenarios independently call `evals/verify_cleanup.py` after
  teardown. It requires complete paged lists and fails on surviving owned
  Providers/apps, query errors or inconclusive responses. The credential's
  disable/delete operations remain separately asserted.
- A synthetic invalid PEM (`AAAA`) only tests real HTTP 400/401 authentication
  rejection, a nonzero exit and no token. Network/TLS/WAF/scope failures do not
  count. Save signature input silently, request the complete user-selected scope,
  and delete the temporary file after owned teardown.
- Positive token issuance remains a Skill capability but requires a fresh real
  ECS signature with the matching IDaaS audience. Without a signer, record it as
  not executed; do not manufacture signatures or add Cloud Assistant permissions.
- Native plugin dry-run validates every declared API's typed parameters and
  POST mapping without sending requests. ECS wire `RegionId` uses
  `--biz-region-id`, while `--region` chooses the endpoint. A mock match alone
  cannot establish valid CLI options.
- First-use plugin status lines are accepted only in the exact released formats
  before a complete JSON response. Other prose, trailing output and malformed
  JSON fail. A parse failure never replays a write. Read-only transient failures
  may use bounded retries; writes stop after their first failure.

## Candidate selection and parallel preparation

Read the complete paged Instances array, including full descriptions. Select
running, non-ServiceManaged test/skill instances and exclude production labels.
Rotate sorted candidates by the case's own session ID. Do not add exclusions just
because a test description says do not touch, do not delete, pre-release, or
automation; these names also never grant permission to modify historical
resources. Record every exclusion reason.

For M2M scenarios, existing M2M apps may prioritize candidates but do not prove
current licensing. Creating and reading back an enabled **owned** app remains
mandatory. Provider-only scenarios have no unrelated app prerequisite. Try at
most eight different candidates, once per candidate. An explicit quota or license
rejection permits another candidate only after reconciling and cleaning owned
partial resources; preserve SDK `Data:` error codes and RequestIds. Unknown write
outcomes require reconciliation, not replay. Never free another case's quota.

## Offline checks and release gates

Run from any directory:

```sh
python3 -B /path/to/skill/evals/validate.py --baseline 898d113 \
  --report-json /tmp/ecs-evaluation-checks.json
```

The default command still runs the full unittest suite. The optional baseline
gate fails on any package change outside `tests/`, `evals/validate.py` and these
two evaluation guides, including changed/deleted business files, platform JSONC,
configuration or untracked package files. It only inspects Git; it never restores
files. Use a report destination outside the worktree. The JSON evidence records
failures, errors, skipped tests, all scenarios, and each declared API's cases.

Offline checks share one sorted scenario inventory and JSONC reader. Duplicate
keys are rejected; comments inside strings remain literal. Generated and
user-defined CLI requests both reach the existing native dry-run gate, which
already deduplicates identical requests. Synthetic IDs remain local to stubs,
native dry-run and isolated catch-all-guarded mock stores; they never reach cloud.
Production dependencies remain Python's standard library.

Local checks cover runtime error handling, pagination, both credential scopes,
PAM grants, signature safety, HTTP/transport failures, independent cleanup,
dependencies/exports, all 23 declared Actions, input shapes, errors and routing.
They do not replace dynamic execution or the standard's >=95% success gate.

For a changed execution package, select functional **and** routing cases and run
fresh static, sufficiency and dynamic checks against its exact commit. Retain
Agent/Model and credential configuration. QUICK_SUCCESS only proves routing;
inspect failed assertions and preserve baseline-control failures. Never present
missing fixtures/entitlements/signers, skipped checks or N/A as valid coverage.
A maintenance-only baseline check proves identical execution inputs, not a newly
executed remote evaluation.
