# Common IDP data model and OpenAPI · reference

The IDaaS `身份提供方（IdentityProvider, IDP）` data model shared by all IDP types, the type URN enumerations, and the OpenAPI operations. Console-based configuration is the primary path; OpenAPI is mainly used to **read/verify** the status of already-configured IDPs, or for automation when conditions allow. Fields defer to the official documentation; anything unconfirmed is marked as a "gap" — never fabricated.

> ⚠️ **Scope**: this reference serves the three supported IDP types (DingTalk / WeCom / Feishu). OIDC / SAML / AD / LDAP IDPs may appear in `list-identity-providers` results — identify them by their type triple and **skip them entirely**: every operation against them (onboarding, configuration changes, verification, even read-only queries) is out of scope for this skill (hard boundary 7 of the main SKILL.md). The OIDC/SAML model details kept below (URNs, config objects) exist for **identification only**.

## Related OpenAPI operations (Eiam, version 2021-12-01)

| Operation | Purpose | RAM Action |
|---|---|---|
| `create-identity-provider` | Create an IDP (write operation; stops at a confirmation point; handle sensitive fields with care) | `eiam:CreateIdentityProvider` |
| `update-identity-provider` | Update the IDP configuration | `eiam:UpdateIdentityProvider` |
| `get-identity-provider` | Read a single IDP's details (read-only, for verification) | `eiam:GetIdentityProvider` |
| `get-identity-provider-status-check-job` | Read the result of an IDP connection/status verification job (read-only). ⚠️ Type-limited: WeCom/AD-LDAP/DingTalk/Feishu only — within this skill's scope (DingTalk/WeCom/Feishu) all three qualify; OIDC/SAML are out of scope entirely anyway (hard boundary 7) | `eiam:GetIdentityProviderStatusCheckJob` |

> Sources: the official OpenAPI portal `https://api.aliyun.com/product/Eiam` and the GetIdentityProvider documentation. The per-parameter schema of `create-identity-provider` is governed by `aliyun eiam create-identity-provider --help` (see "Configuration object structure" and "Supplementary notes on per-type configuration objects"); the per-parameter schemas of `update-identity-provider`/`get-identity-provider-status-check-job` are not collected in this document — verify them in the portal before automating. Additional note: the portal metadata `api.aliyun.com/meta/v1/products/Eiam/versions/2021-12-01/api-docs.json` (357 APIs) matches the CLI's `create-identity-provider` with its 18 top-level parameters, and it **accepts all per-type credentials in one shot** (`--dingtalk-app-config`/`--lark-config`/`--we-com-config`, etc.) **plus** `--ud-pull-config` (sync scope/scheduling/incremental), `--authn-config`, `--auto-create-user-config`, etc. — so in cli mode the IDaaS side of S2/S3/S5 can be completed in a single call (CLI parameters take the **flattened `Key=Value` form**; nested JSON is rejected — for the recipe see step 1 of "The IDaaS-side write path for CLI mode" below; step-by-step instructions are in that section). manual mode still goes through the console.
>
> Strongly interactive steps (DingTalk QR-code authorization, WeCom trusted IP/callback domain, Feishu event callbacks) are usually safer in the console even in cli mode; for the cli/manual boundary and the per-step fallback rules, see `cli-tooling.md`.

### List of available interfaces

Used to read the real state during S7 verification and when producing the S8 handover deliverables; all are read-only (write interfaces are marked separately):

| CLI invocation name | Purpose |
|---|---|
| `list-identity-providers` | Lists the IDPs under the instance. **A single call reads the most status**: includes `TotalCount`, the type triple, `AuthnStatus`, `UdPullStatus`/`UdPushStatus`, plus **`UdPullTargetScope` (sync destination organizational unit) / `PeriodicSyncStatus` (scheduled verification) / `IncrementalCallbackStatus` (incremental)**, which `get-identity-provider` cannot give you. Use it when you just want to quickly check the sync node and the sync cadence — no need to then call the next row for every IDP. ⚠️ **The key set is not fixed**: within one response the number of keys varies per IDP, and **fields without values are simply absent** (e.g., a SAML IDP has no `UdPullTargetScope`; one that has never run a verification job has no `LastStatusCheckJobResult`) — "cannot read a key" = that value is currently empty; **it does not mean the field does not exist, nor that it is unconfigured** |
| `get-identity-provider` | Single IDP details: the type triple, per-type configuration objects (`DingtalkAppConfig`/`LarkConfig`/`WeComConfig`…), `UdPullStatus`/`UdPushStatus`, `AdvancedStatus`, `CreateTime`/`UpdateTime`. ⚠️ **Generally does not contain the sync scope/organizational unit, nor any authentication configuration** (the key set is not fixed; `LastStatusCheckJobResult` appears only after a verification job has run; `UdPullTargetScope` generally does not appear, though occasional responses carry `UdPullConfig.UdSyncScopeConfig{TargetScope, SourceScopes}` — the not-fixed-key-set principle applies equally) — to read the sync scope, prefer `list-identity-providers` (flat field) or `get-identity-provider-ud-pull-configuration`; do not rely on get |
| `get-identity-provider-ud-pull-configuration` | **The authoritative interface for the inbound sync configuration**: `UdSyncScopeConfig.TargetScope` (sync destination organizational unit) / `SourceScopes` (source nodes), `PeriodicSyncStatus` + `PeriodicSyncConfig` (scheduled verification), `IncrementalCallbackStatus` (incremental), `PullProtectedRule` (sync protection thresholds). See the dedicated section below for the structure |
| `get-identity-provider-ud-push-configuration` | **The authoritative interface for the outbound (push) sync configuration**: `UdSyncScopeConfigs[]` (an array; each entry contains `SourceScopes[]`/`TargetScope`), `IncrementalCallbackStatus`/`PeriodicSyncStatus`/`PeriodicSyncConfig`; ⚠️ **no `PullProtectedRule`** — the outbound direction has no deletion protection. The write interface `set-identity-provider-ud-push-configuration` requires `--incremental-callback-status` (same trap as the pull side), and the scope parameter takes the **JSON list** form (see the dedicated section below). See the dedicated UdPushConfiguration section below for the structure |
| `create-identity-provider-status-check-job` + `get-identity-provider-status-check-job` | Initiate and read the result of a connection/status verification job. ⚠️ **Type-limited (server-side `isStatusCheckSupportedType`), not a general-purpose pair**: status-check jobs exist for exactly four IDP types — **WeCom / AD-LDAP / DingTalk / Feishu**. On an OIDC or SAML IDP the create call invariably fails with `405 UnsupportedAction: Current instance status cannot supported this action` (verified live; unrelated to `AdvancedStatus` or any other switch) — the "instance status" wording is **misleading; the real cause is the IDP type**. Do not retry such 405s with different parameter shapes and do not misattribute them to a server-side restriction. (OIDC/SAML/AD/LDAP IDPs are out of scope for this skill entirely — hard boundary 7 — so no check-job is ever run against them from here; the fact above is the explanation to give a user who asks why one cannot be started) |
| `GetIdentityProviderAuthnConfiguration` (**hidden interface**, `--force`; see the ⚠️ block below) | **Current values of the authentication configuration**: auto user-creation switch + `TargetOrganizationalUnitIds`, auto account update, binding switches and match expressions. Used for the S8 handover deliverable's "authentication dimension status" and for the read-before-write preceding an overwrite-style `set` |
| `GetIdentityProviderUserProfileMapping` (**hidden interface**, `--force`) | **Current values of the sync-side field mappings** (`IdentityProviderProfileMappingAttributes[]`). Used to read for the S6 gate verification and the S8 "finalized mapping identifier values" |
| `list-organizational-units` | List the organizational tree; confirm whether source-side departments were mirrored into sub-organizational units |
| `get-organizational-unit` | Details of a single organizational unit |
| `list-users` | List accounts; confirm sync results (account count, whether fields are empty, `UserSourceId`). ⚠️ **Does not return organizational membership** — to find which organizational unit an account hangs under, you must call `get-user` one by one (see below) |
| `get-user` | Single-account details (kebab-case parameters `--instance-id`/`--user-id`). Carries **`OrganizationalUnits[]`/`PrimaryOrganizationalUnitId`** beyond what `list-users` returns; use it for the S7 landing verification of "which organizational unit an account hangs under" |
| `get-network-access-endpoint` | Read the network access endpoint's **current public egress IP ranges** (kebab-case parameters `--instance-id`/`--network-access-endpoint-id`; shared endpoints also go through this interface — just pass `inae_public`). WeCom trusted IPs take this as authoritative. ⚠️ The egress ranges are not officially published and **they change** — read them fresh on every onboarding/troubleshooting occasion; do not reuse historical values or ranges from someone else's handover deliverables |

> ⚠️ **The following interfaces appear in neither the CLI metadata nor the portal api-docs.json, but they genuinely exist on the server.** Probing method: a PascalCase name + `--force` bypasses the CLI metadata validation and hits the server directly; a garbage name returns `InvalidAction.NotFound` as the baseline, while a real interface returns data or a parameter-validation error (e.g., `MissingIdentityProviderId`) — clearly distinguishable. **Invocation form**: `aliyun eiam <hidden-interface-name> --force --InstanceId … --IdentityProviderId …` (the `<hidden-interface-name>` placeholder stands for the PascalCase API name, e.g. `GetIdentityProviderAuthnConfiguration`; write interfaces additionally take `--method POST`); kebab-case + `--force` reports `unknown command`, and without `--force` you get `not a valid api`. Hidden interfaces have no official documentation and no stability guarantee — wherever anything depends on them, it must be flagged:
> - `GetIdentityProviderAuthnConfiguration` — **the authentication configuration is readable**: `AutoCreateUserConfig{AutoCreateUserStatus, TargetOrganizationalUnitIds}`, `AutoUpdateUserConfig{AutoUpdateUserStatus}`, `BindingConfig{AutoMatchUserStatus, MappingBindingStatus, AutoMatchUserProfileExpressions[]}`. IDPs of Feishu, DingTalk orgapp, SAML, and other types all return it. Do not treat the official description of the outer wrapper `--BindingConfig` — "OIDC identity provider account binding rule configuration" — as a restriction on the inner fields: the portal description of the inner `AutoMatchUserProfileExpressions` is the generic "list of rules for automatically matching accounts", and non-OIDC IDPs (Feishu/DingTalk/SAML) likewise return it with values. The authentication-side match rule mentioned in the "mapping identifier" row of the main SKILL.md glossary is exactly this field.
> - **The field mapping interface family (user / OU / group — three structurally identical sets, 10 interfaces in total)** — serves both pull and push IDPs; **the same pair of interfaces auto-detects the direction from the IDP type** (the pull target entity is `idpUser.*`, the push target entity is `user.*`; the server decides from the pull/push affiliation of `IdentityProviderType`), so there is no need to pick different interfaces per direction:
>   - Read current values: `GetIdentityProviderUserProfileMapping` / `GetIdentityProviderOrganizationalUnitProfileMapping` / `GetIdentityProviderGroupProfileMapping` — the user version returns `UserProfileMapping.IdentityProviderProfileMappingAttributes[]{ExpressionMappingType, SourceValueExpression, TargetField}` + **the match key `UserMappingIdentityName`** (the OU version's counterpart is `OrganizationalUnitMappingIdentityName`; the group version has no match key parameter). DingTalk orgapp ships with 6 default mappings; Feishu includes expression-type ones (e.g., `ExtractPhoneRegion(idpUser.mobile)`). ⚠️ **The response after creating a Feishu push contains no `UserMappingIdentityName`** — out of the box there is no match key (DingTalk push ships with `idpUser.mobile`, WeCom push ships with `idpUser.userid`); you must explicitly Set one before matching works at all, otherwise every push is handled as a create and a repeated full sync = duplicate member creation.
>   - Write (**overwrite-style**; read back before changing): `SetIdentityProviderUserProfileMapping` / `SetIdentityProviderOrganizationalUnitProfileMapping` / `SetIdentityProviderGroupProfileMapping`. Parameter recipe for the user version (PascalCase flat form, array subscripts start at 1, same as create): `--IdentityProviderProfileMappingAttributes.<N>.TargetField=<target field>` + `.<N>.SourceValueExpression=<source expression>` + `.<N>.ExpressionMappingType=field|expression` (all three keys required on every entry) + `--UserMappingIdentityName=<match key>` (e.g., `idpUser.mobile`). ⚠️ Two write semantics: ① **an empty list is rejected** (MissingParameter) — mappings can only be replaced wholesale, never cleared; ② **`UserMappingIdentityName` is an unconditional set: omitting the parameter clears the match key** — pushes then lose their matching ability and every full sync is handled as creation. Whenever you adjust mapping entries, you must include the match key parameter in the write.
>   - Query available fields: `GetIdentityProviderUserProfileMeta` / `GetIdentityProviderOrganizationalUnitProfileMeta` / `GetIdentityProviderGroupProfileMeta` — returns the list of mappable fields for that type (with metadata such as whether a field is required and whether it can serve as a match key; **the match key is not fixed and can be changed** — treat these candidates as authoritative). Query it before finalizing the mappings; do not invent field names. DingTalk push has 9 target fields: userid/name(required)/state_code/mobile(required)/org_email/job_number/title/email/remark; the fields usable as match keys for Feishu push are `user_id`/`email`/`mobile`; for WeCom push they are `userid`/`mobile`/`email` (default `idpUser.userid`).
>   - Validate expressions: `VerifyIdentityProviderProfileMappingExpression` — validates only the **variable prefix** (pull must use `idpUser.`, push must use `user.`) and the expression syntax; **it does not check that the field name actually exists** — a mistyped field name is silently skipped at sync runtime (that mapping entry has no effect). Do not count on validation as a safety net.

Write interfaces (stop at a confirmation point; this skill does not execute them on the user's behalf): `set-identity-provider-ud-pull-configuration` (modify the inbound sync configuration: scope/scheduling/incremental/protection thresholds), `set-identity-provider-authn-configuration` (modify the authentication configuration: auto user creation/auto update/account binding), `enable|disable-identity-provider-ud-pull`, `enable|disable-identity-provider-authn`, `bind-user-authn-source-mapping` (manually bind an external identity to an existing IDaaS account; kebab-case parameters `--identity-provider-id`/`--user-id`/`--user-external-id` — used for the "bind to an existing account" remediation when a synced username conflicts). ⚠️ **`set-identity-provider-authn-configuration` is an overwrite-style write** — first read the current values back with the hidden interface `GetIdentityProviderAuthnConfiguration` (`--force`), then write with every field included; otherwise the fields you leave out are silently changed.

CLI pitfalls:

- **`get-identity-provider` returns source-side secrets in plaintext** (Feishu `LarkConfig.AppSecret`; DingTalk `DingtalkAppConfig`'s `AppSecret`/`EncryptKey`/`VerificationToken`; WeCom `WeComConfig`'s `CorpSecret`; etc. — none are masked). Before this interface's output enters the conversation/logs/handover deliverables it **must be programmatically stripped** (filter on the key names `Secret|Password|Token|EncryptKey`); manual eyeballing does not count — this is the concrete landing point of hard boundary 1 of the main SKILL.md in the read-only verification scenario.
- **Raw error output is itself a credential leak path**: SDK/server error texts (Go-style `Post "https://eiam…?AccessKeyId=STS.NZrb…&SecurityToken=…&Signature=…"`) embed the STS credentials in the signed URL query string. Before quoting any raw error into the conversation/logs, programmatically erase the `AccessKeyId`/`SecurityToken`/`Signature` query fields (keep at most the host, path, and error code) — pasting the error verbatim "because it is just an error message" is a leak, the same hard-boundary-1 discipline as the plaintext secrets above. Likewise, when diagnosing the CLI environment, **never dump it wholesale**: no `env`/`printenv` full output and no catting of credential/config files (`~/.aliyun/config.json`, temp credential files) into the conversation — probe by variable name and print presence only (e.g. `[ -n "$ALIBABA_CLOUD_SECURITY_TOKEN" ] && echo "ALIBABA_CLOUD_SECURITY_TOKEN: set"`).
- **In kebab plugin mode, parameters are kebab-case too** (across `get-identity-provider`, `list-users`, `list-identity-providers`, `list-organizational-units`, `create-identity-provider`, …): write `--instance-id` / `--identity-provider-id`; PascalCase flags fail with `unknown flag: --InstanceId … Did you mean: --instance-id`. The sole exception: the hidden PascalCase-only interfaces (the ⚠️ block above) take PascalCase parameters. Mixing the styles always fails; when unsure, check the command's live `--help`.
- **The organizational interface is called `list-organizational-units`**, not `list-organizations` (the latter reports `unknown command`). When unsure, run `aliyun help eiam | grep -i <keyword>` to check the real name.
- **`list-organizational-units` filters**: `--parent-id` (filter by parent organizational unit), `--organizational-unit-ids`, `--organizational-unit-name` (exact), `--organizational-unit-name-starts-with` (left-prefix match), plus `--page-number`/`--page-size` for pagination. Each list item also carries `ParentOrganizationalUnitId`, so a pulled page can be reassembled into tree shape without extra calls.
- **Pagination parameters differ across interfaces**: `list-identity-providers` / `list-organizational-units` page with `--page-number`/`--page-size`, while `list-users` pages with `--max-results`/`--next-token` (it also accepts `--page-number`/`--page-size` — pick one style per script). Do not give them a shared set of pagination parameters when writing verification scripts.
- **`ResourceNotFound.IdentityProvider`** = the IDP no longer exists. On an instance shared by multiple administrators, resources may be deleted mid-course by another admin; when re-checking, first confirm the resource still exists — do not mistake "cannot find it" for your own misconfiguration (the main SKILL.md S8 requires annotating the observation time).

## The IDaaS-side write path for CLI mode

The write path by which the IDaaS side (S2/S5/S6/S7) is completed via `aliyun` in `cli` mode. **Every write command stops at a confirmation point before execution** (main SKILL.md hard boundary 2: the exact command + an explanation of the impact, executed only after the user confirms); all read-back output is **programmatically masked before being displayed** (item 1 of "CLI pitfalls" above). For everything below, **invoke every registered API in kebab-case plugin form** (`aliyun eiam create-identity-provider`, lowercase-hyphenated, with kebab-case parameters); parameter names are governed by the live `--help` output of each. The sole exception is the **hidden interfaces** (the ⚠️ block above): they have no kebab registration (`unknown command`), so they are invoked in PascalCase with `--force` (+ `--method POST` for writes) and PascalCase parameters — that form is reserved for them alone.

1. **One-shot full creation (DingTalk orgapp)**: `aliyun eiam create-identity-provider` (kebab-case plugin form, kebab-case parameters); **nested JSON strings are not accepted** — passing JSON fails with `InvalidUdPullConfig: Flat format is required`. Object parameters take the form `--<object-flag> Key=Value …` — space-separated `Key=Value` pairs after the kebab-case object flag, with the object's inner key names kept as-is (`--dingtalk-app-config AppKey=…`); dotted flag names (`--dingtalk-app-config.AppKey`) are rejected as unknown flags. Command shape:
   ```bash
   aliyun eiam create-identity-provider --profile <p> \
     --instance-id <instance> --identity-provider-name <name> \
     --identity-provider-type urn:alibaba:idaas:idp:alibaba:dingtalk:orgapp:pull \
     --dingtalk-app-config AppKey=<…> AppSecret=<…> CorpId=<…> DingtalkVersion=public_dingtalk \
     --ud-pull-config UdSyncScopeConfig.TargetScope=<ou_id> \
     --authn-config AuthnStatus=enabled \
     --auto-create-user-config AutoCreateUserStatus=disabled \
     --client-token <uuid>
   ```
   Input/output example (sample values; append the global `--cli-dry-run` flag to preview the request without sending it — the recommended preview before every confirmed write):
   ```bash
   # Input
   aliyun eiam create-identity-provider --profile demo \
     --instance-id idaas_dryrun --identity-provider-name dingtalk-pull \
     --identity-provider-type urn:alibaba:idaas:idp:alibaba:dingtalk:orgapp:pull \
     --dingtalk-app-config AppKey=ding_demokey AppSecret=<DingTalk AppSecret> CorpId=ding_demo DingtalkVersion=public_dingtalk \
     --ud-pull-config UdSyncScopeConfig.TargetScope=ou_root \
     --authn-config AuthnStatus=enabled \
     --auto-create-user-config AutoCreateUserStatus=disabled \
     --client-token 9f8b7c6d-0000-4000-8000-1234567890ab --cli-dry-run
   # Output (abridged — the CLI flattens the kebab input into the PascalCase wire-format keys)
   # > Method: POST
   # > Style: RPC
   # > API Version: 2021-12-01
   # > API Action: CreateIdentityProvider
   # > Query Parameters:
   # >   IdentityProviderName: dingtalk-pull
   # >   IdentityProviderType: urn:alibaba:idaas:idp:alibaba:dingtalk:orgapp:pull
   # >   DingtalkAppConfig.AppKey: ding_demokey
   # >   DingtalkAppConfig.AppSecret: <DingTalk AppSecret>
   # >   DingtalkAppConfig.CorpId: ding_demo
   # >   DingtalkAppConfig.DingtalkVersion: public_dingtalk
   # >   UdPullConfig.UdSyncScopeConfig.TargetScope: ou_root
   # >   AuthnConfig.AuthnStatus: enabled
   # >   AutoCreateUserConfig.AutoCreateUserStatus: disabled
   # >   ClientToken: 9f8b7c6d-0000-4000-8000-1234567890ab
   ```
   - ⚠️ **Do not use the wrong type URN**: DingTalk first-party apps use `...:dingtalk:orgapp:pull` (**usable as a creation input**). Misusing the old documentation URN `...:dingtalk:pull` fails with the misleading `UnsupportedAction: Current instance status cannot supported this action` — when you see this error, suspect the URN type first; do not go investigate the instance status.
   - ⚠️ **`--identity-provider-name` varies by type**: for DingTalk/Feishu it may be omitted and the value is ignored (creation succeeds, but the name takes the default `入方向钉钉IdP`); **for WeCom it is mandatory** (omitting it fails with `MissingIdentityProviderName`) yet the value is likewise ignored. After creation, rename via `update-identity-provider --identity-provider-name` (⚠️ **not `--name`** — `--name` fails with `unknown flag`) — **WeCom's update additionally requires `--network-access-endpoint-id`** (omitting it fails with `MissingParameter.NetworkAccessEndpoint`). A rename returns success, but the read-back has **propagation delay** (DingTalk can exceed 6s; WeCom can take roughly 5 minutes) — an immediate read-back may still show the old name; do not treat that as a failure. **Do not chain renames inside the propagation window** (a later rename may not take effect); wait until the read-back name is stable before touching it again.
   - DingTalk's `DingtalkVersion` key under `--dingtalk-app-config` is **required at creation** (`public_dingtalk` / `private_dingtalk`; omitting it fails with a parameter validation error).
   - **Array inputs use 0-based bracket subscripts** — quote each argument in zsh (an unquoted `[0]` triggers glob expansion): e.g., `--ud-push-config "UdSyncScopeConfigs[0].SourceScopes[0]=<IDaaS organizational unit ID>" "UdSyncScopeConfigs[0].TargetScope=<department ID>"`, incrementing the bracket index for each additional entry. Dot-number subscripts (`UdSyncScopeConfigs.1.SourceScopes.1`) are rejected in plugin mode with a "requires index" error.
   - **Outbound (push) creation variant (DingTalk)**: switch the type URN to `urn:alibaba:idaas:idp:alibaba:dingtalk:push`; the credential parameters stay the same (`DingtalkVersion` is still required), and the scope switches from pull's single object to the **`UdSyncScopeConfigs` array**: `--ud-push-config "UdSyncScopeConfigs[0].SourceScopes[0]=<IDaaS organizational unit ID>" "UdSyncScopeConfigs[0].TargetScope=<DingTalk dept_id number>"` (semantics = the organizations/accounts under SourceScopes are pushed under the DingTalk TargetScope department; multiple mappings can be configured). Creation implies `UdPushStatus=enabled`; ⚠️ the push side **has no `PullProtectedRule`** — no deletion protection; for the risks and the write path see Chapter C of the DingTalk reference. **Feishu push is structurally identical**: type URN `urn:alibaba:idaas:idp:bytedance:lark:push`, credentials `--lark-config AppId=… AppSecret=… EnterpriseNumber=…` — all three required; the scope takes the same array form, with `TargetScope` set to the Feishu **custom department_id** (⚠️ not the `od-`-prefixed open_department_id — the reason and the department-creation API are in the Feishu reference's Outbound (push) chapter). **WeCom push is structurally identical**: type URN `urn:alibaba:idaas:idp:tencent:wecom:push` (absent from the documentation enumeration but usable as a creation input), credentials are **dual Secrets** — `--we-com-config CorpSecret=…` (self-built app) and `--we-com-config ContactSecret=…` (contact sync) are **both required** and each is validated live at creation; `CorpId`/`AgentId`/`TrustableDomain`/`AuthorizeCallbackDomain` as usual under the same object flag, plus `--network-access-endpoint-id`; the scope takes the same array form, with `TargetScope` set to the WeCom department ID (root department `1`), default match key `idpUser.userid` — for the source-side preparation (the two trusted-IP spots and the contact-sync permission) and the full procedure see the WeCom reference's Outbound (push) chapter.
   - Remaining object parameters (same `--kebab-flag Key=Value` form): `--lark-config` / `--we-com-config` / `--oidc-config` / `--saml-config`, `--ud-pull-config` / `--ud-push-config` / `--binding-config` / `--auto-update-user-config`, plus `--network-access-endpoint-id` (the WeCom-dedicated endpoint), `--logo-url`, `--client-token` (idempotency token: when cli mode retries the same creation request, pass the same value to prevent duplicate IDP creation; if the creation output is unexpectedly lost, first check with `list-identity-providers` whether it was already created, then retry with the same token — idempotency applies and no duplicate is created). ⚠️ **`PullProtectedRule` cannot be set at creation** (`--ud-pull-config` rejects it as an unknown field) — the deletion-protection thresholds are configured after creation via `set-identity-provider-ud-pull-configuration --pull-protected-rule`.
2. **Read-back verification (immediately after creation)**: `get-identity-provider` (type triple + configuration objects; the output **contains secrets in plaintext** — mask first) + `get-identity-provider-ud-pull-configuration` (sync scope/cadence/protection thresholds) + the hidden interfaces `GetIdentityProviderAuthnConfiguration` / `GetIdentityProviderUserProfileMapping` (current values of the authentication configuration and the sync-side mappings; check them entry by entry against the default mapping tables in the per-type references). Read-back does not match expectations → correct with the step 4 set interfaces; **do not delete and recreate** (deleting an IDP leaves orphaned data — S8).
3. **Switch completion** (read-back shows `UdPullStatus`/`AuthnStatus` as `disabled` while the target is on): `enable-identity-provider-ud-pull` / `enable-identity-provider-authn` (both need only `--instance-id` + `--identity-provider-id`).
4. **Follow-up modifications (overwrite/whole-object semantics; always read back before changing)**: `set-identity-provider-ud-pull-configuration` (parameters are **flattened**: `--periodic-sync-status`, `--pull-protected-rule`, `--ud-sync-scope-config`, etc.; ⚠️ `--incremental-callback-status` is mandatory — bring it even if you only want to change the thresholds); `set-identity-provider-authn-configuration` (**overwrite-style** — include every field, or configuration is silently lost); the hidden interface `SetIdentityProviderUserProfileMapping` (**overwrite-style** write; read back before changing; ⚠️ omitting `--UserMappingIdentityName` clears the match key — the full family and recipes are in the ⚠️ block above); follow-up modifications for push IDPs go through `set-identity-provider-ud-push-configuration` (`--incremental-callback-status` is likewise mandatory).
5. **Trigger the initial full sync (requires explicit user confirmation; hard boundary 3)**: before triggering, pass the S6 gate first — present the current mapping table and match key values (read back in step 2) to the user for **explicit confirmation**; keeping the out-of-the-box defaults is no exception. Then `run-synchronization-job --instance-id … --target-id <IdentityProviderId> --target-type identity_provider` (the other `--target-type` value, `application`, is the outbound direction; **triggering a push for a push IDP likewise uses `--target-type identity_provider`** — for DingTalk/Feishu the statistics land in the `Binded` bucket and verification happens on the downstream side, see C.4 of the DingTalk reference and the Feishu reference's Outbound (push) chapter; **WeCom push statistics buckets are named by operation type (`Created`/`Updated`)**, with the binding established at the first push's `Created`, see the WeCom reference's Outbound (push) chapter; the optional `--synchronization-scope-config` is the sync scope configuration) → `get-synchronization-job --instance-id … --synchronization-job-id <job_id>` to poll the job status (⚠️ this interface's parameters are **kebab**; PascalCase fails with `unknown flag: --InstanceId`; look up the job id via `list-synchronization-jobs`). ⚠️ The terminal state may be `partial_success` — the job record **carries only aggregate numbers (synced/created/failed counts), no failure reasons**; per-account root-cause analysis requires a separate `list-users` query to see who landed and who did not. When an entire WeCom push round fails for all users, the job only reports the wrapper-level error `ALL_USER_EXECUTE_FAILED`; the underlying WeCom error codes (e.g., `WeComError.60129`) must be taken from the console's job details page — `generate-download-url-for-synchronization-job` does not support identity_provider-type jobs. Two common conflict sources (both caused by pre-existing accounts): ① **mobile-number uniqueness conflict** (the source-side user's mobile number is occupied by a pre-existing account; `list-users` masks mobile numbers in its output, e.g., `177******84` — locate the account by prefix + suffix comparison); ② **username conflict** (the source-side username is identical to that of a **pre-existing build_in local account** in the instance — which came first is told from `UserSourceType` and `CreateTime`: an account created earlier than the sync job is a pre-existing one, not produced this time). After root-cause analysis, remediation is one of three options, decided by the user: keep the status quo (the failure merely counts as 1 in the tally; no deletion action) / delete the conflicting side and rerun / bind to the existing account via `bind-user-authn-source-mapping` (see the write interface list above).
6. **Landing verification**: `list-organizational-units` + `list-users`, **querying the sub-organizational units along with the rest** (source-side departments are mirrored into sub-organizational units, and accounts often sit in those sub-organizational units rather than directly under the sync destination organizational unit). ⚠️ `list-users` does not return organizational membership; to find which organizational unit an account hangs under, call `get-user` one by one (see the interface list).

> For the **source-side cooperation** required by each write-path step (which of the app-creation/permission-granting/backfill steps an agent may perform, and which must be done manually), see the "CLI assistance" section of each per-type reference and the step × type capability matrix in `cli-tooling.md` — WeCom's source side is entirely manual; Feishu's backfill-type steps go through the console first.

## IDP type URN enumeration (for identifying the type)

An IDP's type is not a single field; it is expressed as a combination of three fields:

### `AuthnSourceSupplier` (authentication source product)
| Product | Enumeration |
|---|---|
| DingTalk | `urn:alibaba:idaas:idp:alibaba:dingtalk` |
| Alibaba Cloud IDaaS | `urn:alibaba:idaas:idp:alibaba:idaas` |
| WeCom | `urn:alibaba:idaas:idp:tencent:wecom` |
| Feishu/Lark | `urn:alibaba:idaas:idp:bytedance:lark` |
| Azure AD | `urn:alibaba:idaas:idp:microsoft:aad` |
| Alibaba Cloud SASE | `urn:alibaba:idaas:idp:alibaba:sase` |

### `AuthnSourceType` (authentication protocol)
| Type | Enumeration |
|---|---|
| OIDC | `urn:alibaba:idaas:authntype:oidc` |
| SAML | `urn:alibaba:idaas:authntype:saml2` |

### `IdentityProviderType` (sync direction/type)
| Meaning | Enumeration |
|---|---|
| DingTalk inbound (pull) | `urn:alibaba:idaas:idp:alibaba:dingtalk:pull` |
| DingTalk first-party-app inbound | `urn:alibaba:idaas:idp:alibaba:dingtalk:orgapp:pull` |
| DingTalk outbound (push) | `urn:alibaba:idaas:idp:alibaba:dingtalk:push` |
| WeCom inbound | `urn:alibaba:idaas:idp:tencent:wecom:pull` |
| WeCom outbound (push) | `urn:alibaba:idaas:idp:tencent:wecom:push` |
| Feishu inbound | `urn:alibaba:idaas:idp:bytedance:lark:pull` |
| Feishu outbound (push) | `urn:alibaba:idaas:idp:bytedance:lark:push` |
| Standard OIDC | `urn:alibaba:idaas:idp:standard:oidc` — **out of scope: identify and skip (hard boundary 7)** |
| SASE custom OIDC | `urn:alibaba:idaas:idp:alibaba:sase` — **out of scope: identify and skip** |

**pull (inbound)** = syncing accounts from the source into IDaaS; **push (outbound)** = pushing from IDaaS to the downstream side (the full DingTalk push onboarding procedure is in Chapter C of the DingTalk reference; Feishu push is in the Feishu reference's Outbound (push) chapter; WeCom push is in the WeCom reference's Outbound (push) chapter; SCIM-to-RAM is in the background section at the end of this document). This skill handles pull plus the DingTalk/Feishu/WeCom push scenarios **only — OIDC / SAML / AD / LDAP IDPs are out of scope in every respect (identify them in listings, then skip; hard boundary 7 of the main SKILL.md)**; the authentication dimension can be layered onto either direction — an outbound IDP is created with `AuthnStatus=enabled` (the outbound application is simultaneously registered as an OIDC authentication source and can serve QR code logon); when you want sync only, without opening login, the creation recipe explicitly passes `--authn-config AuthnStatus=disabled`.

> ⚠️ **This table's enumeration is incomplete**: variants such as `orgapp` are not listed in the official documentation. When scripts filter IDPs by type, use **prefix matching** (e.g., `startswith urn:alibaba:idaas:idp:alibaba:dingtalk:`); do not compare for full equality against the documented enumeration, or the variants will be missed.

## UdPullConfiguration structure (pull IDPs: Feishu / DingTalk orgapp)

`get-identity-provider-ud-pull-configuration` (kebab-case parameters `--instance-id` / `--identity-provider-id`) returns `UdPullConfiguration`:

| Field | Meaning | Example (Feishu / DingTalk orgapp) |
|---|---|---|
| `UdSyncScopeConfig.TargetScope` | **Sync destination organizational unit** | `ou_xxxxxxxx…` / `ou_root` |
| `UdSyncScopeConfig.SourceScopes[]` | **Source nodes (source side)** | Feishu/DingTalk **have no such field** (their source-side scope can only be set in the source system) |
| `PeriodicSyncStatus` | **Scheduled verification switch** | All three are `disabled` |
| `PeriodicSyncConfig` | `{PeriodicSyncType:"time", PeriodicSyncTimes:[hour]}` | `[4]` / `[3,5]`; the write interface additionally has `PeriodicSyncCron` |
| `IncrementalCallbackStatus` | Incremental callback | `disabled` / **`enabled`** (corresponding to "DingTalk incremental = real-time") |
| `PullProtectedRule` | **Sync protection thresholds** | All are `{UserDeletedThreshold:30, OrganizationalUnitDeletedThreshold:10}` |

**Two key points**:

1. **`PeriodicSyncStatus` (scheduled verification) is a generic IDP field, not a WeCom/Feishu exclusive** — DingTalk has it too, defaulting to `disabled`. The official CLI description of `--periodic-sync-status` is "scheduled verification status — whether to periodically verify data differences between IDaaS and the identity provider", with no type qualifier. **A given official help page not mentioning it ≠ the console lacking it.**
2. **The sync protection thresholds 30 / 10 are identical across types**, and they are independently configurable fields inside `PullProtectedRule` (matching the WeCom reference's advice to "adjust per enterprise size").

The write-side parameter shape differs from the read side: **both create and set are flattened, and neither accepts nested JSON** (nested JSON is rejected at create). `create-identity-provider` takes object flags with space-separated `Key=Value` pairs (`--dingtalk-app-config AppKey=…`, `--ud-pull-config UdSyncScopeConfig.TargetScope=…` — see step 1 of the write path above; ⚠️ the protection thresholds are not settable at creation — see the `PullProtectedRule` note there); `set-identity-provider-ud-pull-configuration` uses multiple kebab-case parameters (`--periodic-sync-status`, `--pull-protected-rule`, `--ud-sync-scope-config`, etc.), and `--incremental-callback-status` is **required** — even if you only want to change the thresholds, you must bring it along, otherwise the request does not go through.

## UdPushConfiguration structure (outbound; DingTalk/Feishu/WeCom push IDPs)

`get-identity-provider-ud-push-configuration` (kebab-case parameters `--instance-id` / `--identity-provider-id`) returns it. The key difference from the pull side is that **the scope is an array**:

| Field | Meaning | Difference from the pull side |
|---|---|---|
| `UdSyncScopeConfigs[]` | An array; each entry `{SourceScopes[] (IDaaS organizational unit IDs), TargetScope (downstream department ID)}` | pull is a single object `UdSyncScopeConfig`; each push entry = one "IDaaS organizational unit → downstream department" mapping, and multiple entries can be configured. `TargetScope` values: DingTalk = the numeric dept_id; Feishu = the **custom `department_id`** (⚠️ not the `od-`-prefixed open_department_id — lark-cli/Feishu native APIs return the `od-` format by default; do not copy it verbatim, read back the `department_id` field value); WeCom = the WeCom department ID (root department is `1`) |
| `IncrementalCallbackStatus` | Incremental callback | Same name, same meaning; ⚠️ the write interface `set-identity-provider-ud-push-configuration` requires `--incremental-callback-status` (**mandatory**; same trap as the pull side, marked required in the metadata) |
| `PeriodicSyncStatus` + `PeriodicSyncConfig` | Scheduled verification | Same as pull |
| `PullProtectedRule` | **Does not exist** | ⚠️ the pull side has the 30-account/10-organizational-unit deletion protection, while the push side has no counterpart at all — there is **no safety net** if downstream data gets written wrong; the only line of defense is a small-scope trial run (hard boundary 3) |

**Write-side shape (changing the scope / the incremental switch)**: the CLI **does not recognize flat dot notation** for the scope parameter of `set-identity-provider-ud-push-configuration` (`--UdSyncScopeConfigs.1.SourceScopes.1` reports unknown flag); you must pass a **JSON list**: `--ud-sync-scope-configs '[{"SourceScopes":["ou_…"],"TargetScope":"<downstream department ID>"}]'`; `--incremental-callback-status` is mandatory.

For the full outbound procedure (source-side preparation / creation / mapping inversion / push verification) see Chapter C of the DingTalk reference (DingTalk), the Outbound (push) chapter of the Feishu reference (Feishu), and the Outbound (push) chapter of the WeCom reference (WeCom). A quick note on the differences among the three push types: default match keys — DingTalk `idpUser.mobile`, WeCom `idpUser.userid`, Feishu none (an explicit Set is required); statistics buckets — DingTalk/Feishu `Binded` (update when an existing binding is hit), WeCom named by operation type `Created`/`Updated` (the binding is established at the first push's `Created`).

## Supplementary notes on per-type configuration objects

- The WeCom configuration object is **`WeComConfig`** (CLI `--we-com-config`): `{AgentId, AuthorizeCallbackDomain, ContactSecret, CorpId, CorpSecret, TrustableDomain}`. ⚠️ **The number of Secrets forks by direction**: **inbound needs only the one `CorpSecret`** — `ContactSecret` (the contact-sync credential) need not be provided; omitting it does not affect creation, connection verification, sync, or QR code logon. When it is not passed, the key will not appear in the response either; its absence from the read-back is normal. **Outbound (push) requires both Secrets**: `CorpSecret` (self-built app, SSO + read) and `ContactSecret` (contact sync, write) are each validated live at creation — if either fails, creation fails (source-side preparation and the full procedure are in the WeCom reference's Outbound (push) chapter).

## Remaining gaps (do not fabricate; fall back accordingly)

- **`get-identity-provider-advanced-configuration` may return `405 UnsupportedAction`** ("Current instance status cannot supported this action") — the interface exists, but the instance state may not support it; do not use it as a general-purpose read interface.
- **`create-identity-provider-status-check-job` is type-limited, not instance-state-dependent**: status-check jobs exist only for WeCom / AD-LDAP / DingTalk / Feishu IDPs; on OIDC/SAML the call always returns the same misleading `405 UnsupportedAction` ("Current instance status…") — attribute it to the IDP type, never retry it as if the instance state were the problem (see the interface list above). OIDC/SAML/AD/LDAP are out of scope for this skill anyway (hard boundary 7) — no operation, this pair included, is ever run against them.
- The per-parameter schemas of `update-identity-provider` / `get-identity-provider-status-check-job` are not collected in this document; verify them in the portal before calling.

## Outbound to RAM (background; not part of this skill's main flow)

⚠️ Do not confuse this with this skill's DingTalk outbound: **DingTalk push is the IDP-side outbound** (a push IDP created under `身份提供方`, covered by Chapter C of the DingTalk reference); the SCIM-to-RAM push in this section is the **application-side** outbound (`应用 > SCIM 接口配置`) — the two configuration surfaces are completely different.

Once accounts are in IDaaS, they can be pushed to RAM via **SCIM**: in RAM, create a Native-type OAuth application → add the `/acs/scim` scope → create an application key (AppSecretValue, visible only at creation) → in IDaaS, under `应用 > SCIM 接口配置`, fill in the SCIM Base URL (`https://scim.aliyun.com`), the token endpoint (`https://oauth.aliyun.com/v1/token`), `client_secret_basic`, and client_id/client_secret → check CREATE/UPDATE/DELETE /Users plus the full-push scope `账户` → one-click push. This segment belongs to the RAM login/sync scenario; expand it only if the customer's goal is "getting IDaaS accounts into RAM" — see the official `use-scim-to-synchronize-accounts-to-ram`.
