# Account lockout and RDP hardening

The most common "cannot connect" root cause in this tier is not the network at
all: it is the Windows account being locked by accumulated failed sign-ins,
usually generated by internet-wide brute force, not by the customer. The
customer's own confusion — "I never typed the wrong password, how can it be
locked?" and "it locked and then unlocked by itself" — is the signature of this
branch (real tickets: an externally-driven lockout that looked like a
self-recovering bug).

## How to recognize it

* Client-side signal: error code `0xd07`, or a message that the account is
  locked / disabled, or a failure right at the password stage.
* Cloud-side signal: the security group accepts the RDP port from `0.0.0.0/0`
  (open to the internet), which is what enables the brute force.
* Guest-side signal (gated query `rdp-account`, `rdp-lockout-events`): a local
  account that is present but failing, and/or recent account-lockout security
  events.

## What this skill does and does not do

It **proves the diagnosis** from the reads above. It **never** unlocks the
account, resets the password, or changes the lockout policy — those are writes,
out of the RO+G scope. Unlocking and hardening are handed to the operator as
console / guest steps.

## Manual remediation (operator, console or guest)

1. **Regain access.** A single successful interactive sign-in (for example
   through the VNC rescue console once the lockout window has elapsed) clears a
   time-based lockout; or an administrator unlocks the local user in **Computer
   Management → Local Users and Groups → Users → the account → uncheck "Account
   is locked out"**. Reference (account-lockout explanation):
   https://help.aliyun.com/zh/ecs/for-safety-consideration-have-lock-the-user-account-the-reason-is-that-login-attempt-or-password-change-try-too-much
2. **Stop the bleeding — narrow the source.** Change the security group so the
   RDP port is reachable only from the customer's own public IP (get it from
   `https://cip.cc` / `https://ip.elisky.cn`). Leaving `0.0.0.0/0` on 3389
   re-locks the account again. See
   [security-group-and-port.md](windows-rdp__security-group-and-port.md).
3. **Harden credentials.** Set a long, complex password (the tickets recommended
   at least a mix of upper / lower / digits, length in the 8-30 range enforced
   by the console reset). If a keypair / no-password channel (Workbench) is
   available, prefer it for routine sign-in so the local password is not the
   thing under attack.
4. **Optional further reduction:** move the RDP listener to a non-default port
   *in addition to* narrowing the source (a non-default port alone is not
   security), and use the console "Reset Instance Password" only with the
   caveat below.

## Password-reset caveat worth stating verbatim to customers

When a password is reset through the ECS console, it **only takes effect after
the instance is restarted from the console**; a restart performed inside the
operating system does not apply it. This is a recurring ticket misunderstanding,
and both the reset and the restart are manual (write) actions this skill
describes but never performs.

## Confidence statement

A query-only check can read a **local** account's state. If the instance is
joined to a domain, the lockout may be governed by Group Policy that these
queries cannot see. In that case report the branch as probable and the fix as
"coordinate with the domain administrator"; do not assert a proven local
lockout.
