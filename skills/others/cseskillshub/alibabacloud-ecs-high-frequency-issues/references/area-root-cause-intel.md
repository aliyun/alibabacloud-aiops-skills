# Area root-cause intel (curated from resolved tickets)

Read the entry for the routed area BEFORE composing its report. Each entry is a
ranking rule adjudicated against a resolved ticket, not a hypothesis: where it
names a PRIMARY cause, that cause leads the conclusion and the verdict line
(SKILL.md, "Final report spine and ranking law", rules 2 / 3c / 3d). Where an
entry says a layer was EXCLUDED by a read, that layer must not be named as root
cause. Ticket ids are provenance for the maintainer; never print them, the `r1406`
/ `snap1` batch labels, or any internal marker in a customer answer (rule 3h).

### web-inaccessible-slow
- region-limited inaccessibility (one city only) is usually carrier-side blocking of the visitor's IP range, not the instance: verify from other exits first; a site down with instance normal suggests DDoS blackhole state on the IP; an HTTPS-only failure with plain HTTP working points to an expired/misbound certificate, not blocking.
- **a domain pointing at a mainland-China instance must rank ICP filing enforcement as the PRIMARY cause, not a later candidate** (r1406 evidence: leg read the layer correctly yet delivered "L5 in-guest listener absent / host firewall REJECT" as primary and ICP blocking as a secondary candidate, while the resolved ticket's cause was filing enforcement). The two families are separated by a read, not by preference: an in-guest `ss -tlnp` showing the port listening plus a local self-test succeeding while the same URL fails from outside excludes the guest layer and leaves filing/carrier enforcement as the confirmed layer; a public-path HTTP probe returning a filing-interception page (403-class with a registration notice) confirms it directly. Do not deliver a mainland domain case as "guest suspected" while the guest layer was never excluded by a read.
### renewal-pricing-discount
- bandwidth downgrade-then-upgrade creates a NEW change order: existing discounts are NOT inherited and refund for the dropped period can be 0; eligibility for free trials is auto-decided by the system (no manual review queue); price/promotion sync can lag minutes after real-name verification completes; a spec that 'does not appear as selectable' in the change wizard is usually a family cap (e.g. u2i core limit) or zone stock-out (check other zones) - not a platform bug; time-limited campaign discounts expire on schedule - confirm the discount's validity window in the order detail before promising a price.
### billing-attribution-bill-check
- bill lines are often attributed to the wrong product: OSS, Bailian and CDT public-network traffic charges are routinely mistaken for ECS spend - always group the bill by product before concluding; arrears freeze releases pay-as-you-go items first.
### access-block-layered
- two host firewalls can be active at once (iptables/ufw AND firewalld on the same guest) - a port allowed in one layer stays blocked; enumerate every in-guest firewall service before concluding; conversely, a port fully allowed but with NO listener means the service itself is dead or not enabled at boot - run ss -tlnp and systemctl is-enabled before touching any rule; after a remote tool or script edited system config, a previously fine service can fail at boot - diff recent config changes before blaming the platform. Evidence-binding: naming the security group as root cause REQUIRES quoting the specific missing/deny rule actually read from DescribeSecurityGroupAttribute (direction, port, source, priority - watch enterprise SGs whose default policy denies egress); if the read allows the traffic, SG is EXCLUDED - a service-down, a no-listener port or an in-guest DROP rule read live must be delivered as the primary confirmed cause, not ranked behind a speculative SG suspicion. The guest firewall IS readable whenever the Cloud Assistant agent responds AND the customer consents to the specific read: run iptables -S / nft list ruleset / firewall-cmd --list-all through the gated path (`--allow-guest-read`, or the area's `--confirm` token) and quote their output; leaving the guest layer unverified while the agent was reachable is a report defect, and an unverified guest layer must never be ruled OUT as the blocking layer.
- **OSS bucket-policy whitelists and AccessKey network-access restrictions are two different layers - never substitute one for the other** (r1406 evidence: leg attributed a failed caller to an `acs:SourceIp` bucket-policy allow-list while the resolved cause was a network restriction bound to the AccessKey itself). When the symptom is "this caller/this key is denied from this network while other keys or other networks work", check the key-scoped network restriction before any resource-policy theory: a resource policy explains who may touch a bucket, a key restriction explains from which source addresses the key may be used at all. The key-scoped restriction is read from the RAM/AccessKey attribute layer, not from bucket APIs; when that layer is not readable under the current identity, deliver it as an explicit UNVERIFIED candidate that would confirm/deny this exact symptom - do not conclude the bucket policy is the cause merely because it is the policy that was readable.
### web-service-runtime-config
- site hangs or 5xx under normal instance metrics is usually the web stack itself: PHP-FPM pm.max_children exhausted at full CPU, or nginx worker/connection limits against high connection counts - pull the slow/error log and process counts before network layers; a suddenly closed/timeout SSH or service port can be a trojan or exploited service overwriting firewall rules - check for unexpected listening processes; connection refused (not timeout) with the instance running means nothing listens on that port - systemctl is-enabled/is-active plus ss -tlnp reads decide the case: a stopped or boot-disabled web service is the primary confirmed cause, do not redirect suspicion to security groups when the rule read shows the port allowed.
### instance-start-stop-anomaly
- stuck Stopping is usually in-guest: pending Windows update or a hung process blocking shutdown; stuck Starting often traces to custom-image network config (netplan/cloud-init) failing to boot.
- when a boot/login failure follows a disk re-attach or a disk removal, a stale `/etc/fstab` entry is the FIRST cause to state, not the second: quote the fstab UUID against `lsblk` and deliver "the fstab entry has no live device, so boot stalls in emergency mode" as the primary conclusion before any disk-full or OS-layer theory (snap1 ticket T-B36F1620: leg read the fstab correctly and still published root-disk-96%-full first, demoting the true cause to a #2 candidate, which is a ranking defect of the report).
### instance-state-diagnosis
- OS unresponsive with normal CPU can still be disk-IO saturation (iowait) or inode exhaustion of the root partition from many small files - check IO and inode, not just CPU/memory gauges; low free memory triggering OS cache reclaim/page-out (visible as kswapd0 busy and IOPS pinned with idle CPU) also shows as spiking disk IO - check free memory and swap activity, not just CPU/memory gauges; a 100%-full system disk breaks logins, databases and web services at once - check df before deeper theories; when the agent is reachable AND this turn carries guest consent, df/free/uptime and per-directory du ARE readable read probes (non-mutating, but gated exactly like every other in-guest read) - a resource hypothesis stated without its measured number is incomplete: get consent, run the probe, cite the number, then rank; without consent the layer is UNVERIFIED, never 'clean'.
### unsubscribe-refund
- a refund/unsubscribe that silently fails is usually an unchecked agreement box or an unpaid pending order blocking the flow - walk the customer through the order page state instead of quoting generic refund rules.
### remote-connection-entry
- Workbench command failures like 'workbench: command not found' mean the CLI is not installed in the guest, not a credential problem: check installation before token flows; repeated correct-password rejections are often the in-guest account-lockout policy (Windows Lockout threshold / linux pam tally2) - check lockout state before blaming SG or credentials.
### host-intrusion-cleanup
- malicious 'cache' dirs under web roots are webshell drops: compare file mtime against access logs to build the intrusion timeline; violation locks hitting several accounts from the same campaign are risk-control actions, not per-instance faults; exposed php-fpm (or old panel software) is the top entry point - look for reverse-shell processes spawned by php-fpm/nginx workers; when a web service is stopped AND CPU is pinned by an odd process, rank a coin-miner replacing the service before benign causes.
- **many private source addresses in the same VPC/subnet converging on one instance and one port is a legitimate acceleration/proxy back-source pattern first, an intrusion pattern second** (r1406 evidence: leg declared "lateral movement / intrusion signature" for four same-segment private IPs while the resolved cause was Global Accelerator back-to-origin traffic). Before naming lateral movement, exclude the fan-in pattern by reading what the sources actually are: a genuine compromise shows attacker-controlled processes, new persistence or outbound C2 in the same instance, not just inbound connection volume; back-source traffic shows a stable port, no unexpected guest process and no outbound anomaly. An elimination of the intrusion reading must be produced by a read that covers it - and conversely, ruling IN intrusion on connection counts alone, without the process/persistence/outbound reads, is an unsupported conclusion.
### public-ip-guide
- a fixed public IP and an EIP are mutually exclusive on one instance: the fixed IP is CONVERTED into an EIP (ConvertNatPublicIpToEip, one way and irreversible) before an EIP binds - never say the customer should "release" the fixed IP, because release is irreversible and loses the address; 'IP changed / cannot bind EIP' tickets usually trace to this - state the constraint before listing generic causes; also, an instance generally cannot reach its own public IP/EIP from inside (hairpin not supported) - tests from the guest to its own public IP failing is expected, not a fault; verify from an external client.
- "no EIP" is only claimable from an actual `DescribeEipAddresses` read of the region, never inferred from `DescribeInstances` (R13 A-batch: a leg wrote "EIP reads (already done via the attack area): no EIP" without ever dispatching it). The decisive signature is an EIP that exists in the region with `Status=Available` and no associated instance while the instance still carries a fixed public IP: that is the mutual exclusion made visible (the allocation succeeded, the bind could not), so read it region-wide, quote the address plus its AllocationId, and name the conversion path instead of ranking DNS or bandwidth above it.
### db-on-ecs-diagnosis
- 'program cannot find the server' with normal ping is often the database layer: full transaction log, exhausted connection pool, or bind-address changes - escalate to DB checks after the network layer is clean; when the DB is RDS-managed, check the RDS-side whitelist/SG inbound port (e.g. 1433) as a first-class cause, not only ECS egress rules; a full system disk silently breaks databases and panels - rank df/inode checks high; a missing monitoring agent (argus/cloudmonitor plugin) is a frequent concrete cause when metrics are blank or DB monitoring alarms never fire - verify agent installation before blaming account visibility.
### spec-change-purchase
- general-purpose ECS cannot hot-migrate to GPU specs (different platforms): the path is create-image then purchase a GPU instance from it; never promise an in-place upgrade across families; a blank or stuck pricing/quote page in the console is often browser compatibility (cache/extensions/an unsupported browser) before it is a platform fault - rule out the browser first.
### ssh-connection
- repeated failed logins from a client IP can be locked out by in-guest fail2ban or the hosting panel firewall - verify server-side bans before blaming security groups; correct password refused = check sshd_config PasswordAuthentication no first and cite the actual sshd -T passwordauthentication read value as the confirming evidence; instances can effectively have two egress IPs (one per NIC/EIP) - pin the exact source IP before asking the customer to whitelist; cross-border link jitter on overseas/HK endpoints is a last-resort explanation only - after in-guest CPU/IO, listeners and firewall layers are proven clean. NEVER attribute the block to the security group unless you quote the exact missing or deny rule (direction, port, source) read from DescribeSecurityGroupAttribute for THIS instance's real SG ids; when that read shows the port allowed, the SG layer is EXCLUDED and any in-guest anomaly you can read (sshd config, fail2ban ban list, iptables DROP) becomes the primary confirmed cause. All decisive sshd facts are readable via read probes when the Cloud Assistant agent responds - sshd -T effective config, ls -l /etc/ssh/sshd_config.d, fail2ban-client status. They are non-mutating but NOT ungated: they run inside the customer's machine, so they need the same `--allow-guest-read` consent as any other guest read (the area auto-baseline is withheld without it and the layer prints UNVERIFIED). Once consent is given, quote their output instead of ranking sshd hypotheses unverified.
### windows-rdp
- RDP failure with the instance running is often in-guest: terminal-server grace period expired or licensing error, self-signed cert / NLA encryption-level mismatch, or the RDP listener disabled - enumerate these before blaming security groups; custom ports (e.g. 8002) additionally need the Windows Firewall allow rule, an SG rule alone is not enough; malware/RDP-brute-force campaigns saturate CPU and may ransom-encrypt data disks - the trigger is almost always 3389 open to 0.0.0.0/0: insist on source-restricted SG rules for RDP; rank that first when login was shared; a data disk showing 0 free space right after attach points to a full or uninitialised partition, not disk failure; for overseas/mini instances, cross-border congestion is a last-resort explanation - only after in-guest CPU/memory/disk and service listeners are verified clean.
### instance-relocation-guide
- instance CPU architecture (ARM vs x86) is fixed at hardware level: relocation/conversion always means create-image then buy the target family - never offer an in-place architecture switch.
### disk-expand-diagnosis
- after a paid disk expansion the size only appears once the in-guest partition AND filesystem are extended; 'memory/disk still shows old usage' after payment is usually this missing step, not a billing failure; /etc/fstab entries pointing at removed or re-attached disks make boot stall in emergency mode and break mount -a - read fstab UUIDs against lsblk UUIDs and rank a stale fstab entry as the primary confirmed cause when a reboot preceded the failure; when df reports no free space on the system disk, that read alone confirms login/panel/service failures - deliver it as the primary finding, not one candidate among network theories; the fstab/lsblk facts are readable without customer help: the instance-state-diagnosis entry tool collects cat /etc/fstab + findmnt + free -h + df -h as one batch of non-mutating probes, but only when this turn carries `--allow-guest-read` (the dispatcher passes `--guest-baseline` only after consent) - run it, quote the read, and otherwise report the tier UNVERIFIED; a fstab UUID absent from the live mount table is the confirmed stale-entry cause.
- 'Expanded but df still shows old size / still full' has exactly THREE gates - console ResizeDisk payment, in-guest partition grow (growpart), filesystem grow (resize2fs on ext4, xfs_growfs on XFS); the API disk size read proves only gate 1. When the API shows the new size but df shows the old, land the confirmed determination 'guest partition or filesystem not grown' and give the exact three-step command sequence - enumerating it as one candidate among billing/refresh theories is an incomplete report (R12 ticket evidence: the correct direction was ranked as a hypothesis while the deterministic three-gate ruling was never stated).
- **which partition is grown must be decided by the live layout, not assumed** (r1406 evidence: leg prescribed the generic growpart + resize2fs sequence while the resolved cause concerned a second partition on the system disk). Read `lsblk` (plus `findmnt`) before naming the grow target: when the disk carries more than one partition, growpart needs the specific device-partition index and the target filesystem may be on a different partition than the one the customer assumes; if the layout shows the new space unallocated beyond the last partition, the correct ruling is extend the existing partition, whereas a disk whose remaining space sits outside any partition cannot be grown by the generic sequence at all. Quote the read layout next to the command you give - a grow command without the layout it applies to is an unverified instruction.
### service-escalation-guide
- local/edge regions (e.g. Fuzhou) have been progressively retired: instances sitting stopped there with no in-guest change are usually affected by a region closure - check the region status before debugging the guest.
### cloud-assistant-diagnosis
- when an OOS template or Cloud Assistant invocation fails with permission errors, check the invoked role/service-linked role actually exists and is correctly assumed - template + role misconfiguration is a frequent root cause, not the command itself.
- the Cloud Assistant command channel dies with the credential it depends on: removing an instance's SSH key pair, or disabling PowerShell (or replacing the default shell) on Windows, breaks the channel, so "the assistant reports the command failed / the instance is unreachable to the assistant" is usually NOT an OOS permission problem - name the removed key pair / disabled PowerShell as the primary cause and the way to restore the channel (re-bind a key pair through the console, re-enable PowerShell), rather than leaving it as a candidate (snap1 tickets T-2A646901, T-F44877E4).
- a failed OOS/backup task that names the backup or anti-ransomware service is not evidence that the assistant is broken: the originating task's own service error is the cause, and the assistant merely reported it.
### slb-backend-diagnosis
- customers often name an ECS instance 'SLB' by mistake - first verify what the resource actually is (instance vs load balancer) before running LB-side checks; billing attribution follows the real resource type.
### hbr-backup-diagnosis
- backup resource packages are product-scoped: an HBR/backup pack cannot offset other products' bills and vice versa - check package applicability before any arithmetic on charges; unexpected 'backup-related' bills are often CDT public-network traffic overage, not snapshot capacity - split the bill by product line first.
- a KEEP_LAST_STATE-class backup alert that persists after the backup job recovered is the alert's own retention behaviour, not a task to clear by hand: it auto-clears once the policy's detection cycles (~3) observe the healthy state, so the deliverable is the wait-and-verify instruction, not "delete the rule manually" (snap1 ticket T-6ADE959C: leg correctly called the residual alert normal but then instructed a manual rule deletion as the root cause).
### ssl-cert-deployment
- 'site shows certificate error' is usually the cert itself: expired, or issued for a different domain (www vs apex mismatch) - inspect the served cert before blaming DNS; behind CDN the cert must be deployed/synced on the CDN side too - origin-only renewal leaves the old cert served.
- when HTTPS serves a certificate that belongs to ANOTHER site on the same server (for example the main domain's certificate answering for a subdomain), the FIRST cause to state is nginx SNI fallback: the `server` block whose `server_name` matches the requested host has no `ssl_certificate`/`ssl_certificate_key` (or does not `listen 443 ssl`), so the handshake falls through to the default server block and nginx serves THAT block's certificate. Fix the matching block's TLS pair, not the certificate; "certificate SAN does not cover the host" is only the second candidate (ticket T-F9AA3466).
### linux-permission-repair
- after 'replace operating system' the instance boots but login or panels fail: the selected image differs from the expected distro/version - verify image ID vs OS family first; the system disk is wiped by the replace while data disks are retained, so warn before any replace action.
### disk-pl-change-guide
- AutoPL/cloud-disk burst performance is charged pay-as-you-go when burst credits are consumed: customers routinely see 'unexpected IO bills' from bursting - read the disk category and burst settings before calling the charge an error; disk category compatibility gates replacement/migration - e.g. some categories are not offered in certain regions or instance families, verify category-zone-family compatibility before proposing a plan.
- After any PL/burst upgrade or AutoPL change, the ATTACHED instance family's per-disk BPS/IOPS ceiling still caps realized performance: read both the disk PL limits and the instance family storage limits, state both ceilings and name which one binds. If the instance cap is lower, tell the customer upgrading the disk further yields nothing and advise upgrading the instance family instead (R12 ticket evidence: a correct AutoPL one-way verdict still missed the instance-spec BPS/IOPS cap that was the customer's real bottleneck).

### bandwidth-modify-guide / public-bandwidth-billing-check
- measured download slightly below the ordered peak (e.g. 0.92 Mbps on a 1 Mbps order) has TWO stacked normal causes that must BOTH be stated, not just the first: (1) bit-vs-byte conversion and spec-ceiling behavior (1 Mbps ~= 128 KB/s, the ceiling working as designed); (2) low-bandwidth shared tier carries NO SLA - peak-hour shared-pool contention throttling below the ceiling is expected and is the usual customer-complaint root cause. Confirmed determination: name both layers, put "no-SLA shared tier" as the reason real throughput dips below ceiling during busy hours, then remediate (raise peak bandwidth, switch to pay-by-traffic for burst headroom, or test off-peak to demonstrate the pattern). Reporting only "at ceiling, normal" while the customer complains of variability is an incomplete verdict.

### preemptible-instance-guide
- the spot discount covers ONLY the instance specification (compute) charge line - images, disks (system and data), public bandwidth and snapshots are still billed at their own rates; on release the instance compute stops billing but attached pay-as-you-go disks and snapshots persist and keep billing, and local-disk data is lost irrecoverably; when explaining "unexpected residual spot bills", split the bill by product line and name the data-persistence consequence explicitly (R13 ticket evidence: correct discount-scope ruling still missed the cloud-disk / stopped-mode data-persistence point the human agent tied to the bill).
### punishment-appeal-guide
- a blocked or released resource flagged by risk control is not an ECS configuration fault: distinguish quota-driven limits from punishment limits - raising QUOTA beyond the published ceiling requires an offline business/SA channel, not an appeal ticket; when the read shows a punishment flag, give the appeal path AND state the quota ceiling rule with the channel that can raise it, so the customer is not sent appealing a limit that an appeal cannot change. The two channels MUST be delivered as separate confirmed determinations, never merged into one hedged "escalate / review" line: if the ticket text hints at a large quota or repeated limits, the report names "beyond-quota -> offline business/SA channel" as its own ruling alongside "violation -> appeal path". When the punishment/quota FLAG itself is not readable from the ECS side, that is NOT a reason to withhold the ruling - the two-channel mapping is platform-policy knowledge needing no read (ranking law #4): quote the ticket's own signal (limit amount, repeat count, block wording) and deliver both determinations conditionally ("if this is a quota ceiling -> offline business/SA channel; if a violation flag -> appeal path"), never end at "not visible to my queries" (R13 leg evidence: round-2 run still stayed partial by declaring the risk verdict invisible and stopping there).
### billing-mode-selection
- fixed-bandwidth (pay-by-bandwidth) mode bills the peaked bandwidth, NOT total traffic - cumulative usage does not appear as a billing quantity, so "I barely used it but got billed" is a mode-semantics misunderstanding, and "traffic looks low yet bill is X" needs the peak-bandwidth read; pay-by-traffic is the mode that bills total outbound traffic. These are platform-policy facts readable without any API - state the mode-to-billing-quantity mapping as the confirmed determination before any usage arithmetic (R13 ticket evidence: leg hedged on its own API gap for utilization metrics instead of ruling the deterministic mode fact the human agent stated).
- charge-type conversion applies to the INSTANCE only: a pay-as-you-go cloud disk (or snapshot) attached to it does not follow the instance into the subscription, keeps billing, and cannot be released by converting - so "I converted to a commitment but the bill did not change" is the data disk, and a container/Pod that cannot be deleted because its volume is pinned by a still-attached pay-as-you-go disk is the same fact seen from the workload side. Name the persistent attached resource and the release-the-disk step, not only the instance's mode (snap1 ticket T-2E0A8DF0: leg asserted the data disk follows the instance and therefore has no effect, the opposite of the resolved cause). Release-and-repurchase is likewise the only path for a new-purchase-only campaign (for example a 99-class first-purchase offer): an expired offer cannot be re-priced in place on the existing instance.
### burstable-instance-guide
- on entry-level/shared instances a "website slow" complaint is usually BANDWIDTH-WEIGHT arithmetic, not a front-end defect: the homepage HTML curl returns (tens of KB) is NOT the page weight - parse the HTML for referenced subresources (img/js/css, including third-party CDN links), fetch or HEAD each, and sum to a total page weight; compare that weight against the ordered peak bandwidth (1 Mbps ~= 128 KB/s) and state the load-time estimate as the confirmed determination ("~22 MB page on a 3 Mbps tier ~= 60s+ first load; peak-hour shared tier has no SLA"), then remediate (raise bandwidth, compress/defer subresources, put static assets on CDN). Finding mixed-content or missing-CDN observations does NOT replace this weight ruling - reporting a front-end theory while omitting the bandwidth-vs-weight estimate is an incomplete verdict (R13 ticket evidence: a clean external probe of the 20KB homepage was answered as front-end/mixed-content while the human agent's truth was the 22.6MB total page weight saturating the 3Mbps tier).
- a burstable/shared instance that reports sustained ~100% CPU with slow response is usually CREDIT EXHAUSTION, not a defect: once its CPU credits run out the instance is throttled back to its baseline performance share, so the confirmed ruling is "the instance exceeded its credit balance and is capped at baseline - raise the credit ceiling / switch to unlimited mode / move to a compute-optimized family", with the sustained-CPU metric as the evidence. Delivering instead "pay-as-you-go monthly billing after the change" and omitting the credit ceiling leaves the key root cause unstated (snap1 ticket T-A0EA7DEF).
### custom-image-lifecycle
- when a custom/migrated image "does not come up" or an old image fails after a platform lifecycle change, the decisive fact is the **guest user-space/toolchain compatibility against the target generation** (glibc and kernel-ABI level), not just the image's EOL status: read or ask for the image's OS and libc version (`ldd --version`, `uname -r`) and state which hypervisor/instance generation the image can and cannot boot on - "the family or region was retired/EOL" is the direction, the libc/ABI mismatch is the root cause the customer can act on (r1406 evidence: leg stayed at the EOL/migration direction and never named the version incompatibility the resolved ticket identified). Do not map an old image's failure onto a known customer case without the version read; when the version read is unavailable, deliver it as the explicit check that decides the case rather than a generic rebuild recommendation.
### instance-state-diagnosis (spec-change limit)
- a preemptible (spot) instance does not support an in-place specification change at all: when the console or API refuses the change, the cause is that platform limit, not stock-out of the target spec - do not answer "the new spec is out of stock" and do not recommend another spec, because no spec is changeable on a spot instance; the workable paths are releasing and recreating as spot, or converting to a non-preemptible instance first (snap1 ticket T-98C2133E: leg named spot direction and the main root cause yet mislabelled the refusal as a stock limitation).
### disk-attach-os-visibility
- a data disk just attached to a Linux instance shows up with no filesystem and cannot be mounted: an NTFS-formatted disk is unreadable without the ntfs-3g driver and `lsblk`/`blkid` show it as a raw/unknown device - naming it "a blank disk" is wrong; the deliverable is the filesystem read plus installing ntfs-3g (or re-attaching to a Windows host) so the data is reachable, together with the persist-the-mount step (snap1 ticket T-8BFA2662: leg found the missing fstab entry but judged the disk raw and never named ntfs-3g).
### smtp-block-diagnosis
- port 25 blocked by the platform is almost always triggered by the workload itself: look for a malicious or misconfigured relay process (an exposed ActiveMQ/Java mail consumer is a known source) generating bulk outbound mail before answering with only "platform blocks 25 + adjust the security group" - the malicious process is the root cause to land, and the security-group/platform layer is the follow-up (snap1 ticket T-BE62B4C9).
### ram-policy-diagnosis
- a policy that denies an API call for one caller is often not the policy content: an unset or wrong ENVIRONMENT variable (region id, account id, endpoint) makes the call fail in a way the policy is then blamed for - lock the environment/config read as the root cause instead of listing it as the third candidate (snap1 ticket T-E4CE984B).
### login-credential-repair
- when a login stops working after a console-side change and the ticket text already points at the key pair / password being removed, that removal IS the root cause: the key pair bound to the instance was deleted (or re-bound elsewhere) and the assistant/temporary-key channel is a side effect, not the cause - state the removal and its restore path (create a new key pair and re-bind it, or set a password through the console) instead of re-routing the answer to the assistant channel (snap1 ticket T-2A646901).
### intranet-egress
- when a private-network path fails, the in-guest sshd password-auth setting is NOT the leading cause merely because a read shows it disabled: state the private-IP reachability finding first and keep the sshd layer behind it unless the symptom is actually an authentication refusal (snap1 ticket T-408A7B6F: sshd-disabled was ranked first while the private-IP root cause was known).
