# M4: Support-Process Guidance (generic steps, expectation management)

**Evidence status of this module.** The tier was authored with **zero
verified official help documents** (the documentation search returned no
hits), so this module deliberately contains **no console button paths, no
URLs, no hotline numbers, no response-time figures and no service-plan
terms**. Those slots may only be filled later from documents fetched and
verified in-session; until then everything here stays generic and says so.
Fabricating a channel entry to look helpful is the single most damaging
failure mode of this tier (SKILL.md Absolute Rule 5).

## What this guide can and cannot do

| Can do | Cannot do |
|---|---|
| Classify the demand (follow-up / complaint / technical / adjacent) | Query, verify or update any ticket state |
| Structure the customer's materials into a package | Expedite, prioritize, reassign or withdraw a ticket |
| Corroborate affected instances with two read-only ECS reads | Read the customer's inbox/ticket thread |
| Give generic self-help steps | Promise deadlines, escalation success, compensation |
| Hand off with retained context | Decide responsibility or service-quality verdicts |

## Generic follow-up steps (deliver these, with the caveat)

1. Follow up **on the original ticket thread**, using the prepared package:
   ticket number, customer-stated timeline, business impact, deliverable
   expectation. Use the official support entry of the console the customer
   already uses -- confirm the current entry there; this guide quotes no
   path.
2. State the ask as one concrete, deliverable step (for example: "a first
   progress update before end of today"), not a demand for a fix deadline.
3. Do **not** open parallel tickets to go faster: they split context; the
   package explicitly says "follow-up on ticket <id>".
4. If a broad service incident may explain the wait, the customer can check
   public service-status announcements themselves -- the only progress
   substitute this guide may point to (the guide reads no systems itself).
5. Ask human support for the escalation/complaint route when the package
   is complete; requesting escalation is legitimate, obtaining it is a
   human decision this guide cannot pre-announce.

## Complaint steps

1. Pin the subject: timeliness / outcome / attitude / other (one primary).
2. Facts first: timeline (customer-stated), what was asked, what came back,
   impact. No blame language, no diagnosis of the technical root cause.
3. Deliverable ask only: a review of the handling, a written response, a
   named follow-up owner. Compensation and responsibility findings are out
   of every wording (expectation discipline in escalation-package.md).
4. If the complaint coexists with an unresolved technical problem, the
   technical area goes first (handoff-matrix.md); a complaint never
   substitutes for fault resolution.

## High-frequency misconceptions this guide must defuse

- "Chatting with the assistant has already chased my ticket" -- no: this
  guide prepares material; the submission happens by the customer in the
  official channel, and nothing is promised about the result.
- "A brand-new ticket will be handled faster" -- duplicate tickets split
  context; keep one thread.
- "Urgent words make it urgent" -- priority is set by human processes; the
  package contributes evidence (impact, timeline), nothing more.
- "Why does another customer have a dedicated engineer" -- service-plan
  differences exist; their terms must be confirmed via official plan
  documentation, never asserted from memory by this guide.

## Expectation-management phrases (admissible wording)

- "I cannot see the ticket's handling state, so everything below is your
  stated timeline."
- "The package is ready for you to submit through the official support
  entry; I cannot submit or chase it for you."
- "No response deadline can be promised here; the ask inside the package is
  for one concrete, deliverable next step."
- "For service-plan terms, complaint-intake specifics and current entry
  points, confirm via official channels -- this guide only uses verified
  text and says so when a detail is unverified."

## When asked for unverified channel details

Say: the entry is intentionally not quoted because it is not verified
within this session; recommend the customer's usual console support entry
or the official site search for the current document; offer to work from
any document text the customer pastes (the skill can restate verified
pasted content, but never invents it).
