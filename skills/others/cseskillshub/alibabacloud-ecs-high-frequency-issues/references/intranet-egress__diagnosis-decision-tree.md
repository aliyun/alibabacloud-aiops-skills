# Diagnosis Decision Tree

The tree implemented by `scripts/areas/intranet_egress/ecs_connectivity_diagnose.py`. Steps D0 to D6
run in order; each step either produces a finding, routes to a branch, or ends
the diagnosis with an attribution.

The organizing principle: a connectivity complaint is only diagnosable once
three things are pinned down - **who initiated**, **what the target is**, and
**which layer dropped the packet**. Everything else is noise until those are
known.

## D0 - Input gate

Require direction, target and instance locator. When something is missing, ask
for exactly the missing items and nothing else, then stop.

The script returns `VERDICT: NEED-INPUT` with a `missing_input` list and
`STATUS: FAIL`. Never guess a region, an instance ID, a port or a direction to
make the run proceed.

Direction-specific requirements:

| Direction | Also required |
| --- | --- |
| `egress` | `--target` or `--target-ip` |
| `ingress` | `--port` |
| `internal` | `--peer-instance-id` or `--peer-ip` |

## D1 - Asset ownership

Resolve the caller identity, then look for the instance by ID, private address
or public address in the given region under that account.

| Result | Meaning | Route |
| --- | --- | --- |
| Instance found | Ownership confirmed | Continue to D2 |
| No instance matched, queries succeeded | The address is not an ECS instance of **this** account | `ATTRIBUTION: ownership`, `VERDICT: OUT-OF-SCOPE`. Either another Alibaba Cloud account owns it, or it is not an Alibaba Cloud asset at all: a customer data center, another provider, or an office network. Stop and ask who owns the machine and where it runs. |
| Queries failed | No evidence could be read | `STATUS: FAIL` with the degradation log |

This step exists because mis-routing is common and expensive. A customer
describes a fault in detail, and only later learns the server sits under a
different account or is not a cloud asset. One query settles it.

Cross-account resources are not readable from here. Say so plainly rather than
reporting "instance not found" as if it were a network fault.

## D2 - Direction split

Re-derive direction from the initiator and the target. **Do not trust the
category a case was filed under.** Filed categories and real fault directions
frequently disagree: an outbound failure gets filed as a mutual-access problem,
and an inbound failure gets filed as an egress problem.

| Initiator -> Target | Direction | Branch |
| --- | --- | --- |
| Outside client -> instance port | `ingress` | D3 ingress |
| Instance -> internet endpoint | `egress` | D3 egress |
| Instance -> instance private address | `internal` | D3 internal, then split by same VPC / cross-subnet / cross-VPC |

## D3 - Cloud-side reads

Non-mutating queries, run automatically. Which ones run depends on direction.

**All directions:** read back every security group attached to the instance and
evaluate the probe against the rules. Interpretation details, including blanket
drops, priority shadowing and the ICMP trap, are in
[security-group-readback.md](intranet-egress__security-group-readback.md).

**Egress**, in this order - the first blocking finding is the answer:

1. Does the instance have a public address or an EIP? If not, is there an
   `Available` NAT gateway in the VPC? Neither means there is no cloud-side
   egress path at all.
2. If a NAT gateway exists, does an SNAT entry cover this instance's VSwitch or
   its private address? A NAT gateway without covering SNAT still fails.
3. If the instance has a fixed public address but zero outbound bandwidth, no
   traffic leaves even though the address exists.
4. Is there an all-protocol, all-port Drop rule spanning the whole destination
   space in the egress direction? This is the classic blanket deny-out shape,
   including rules pasted from an unrelated source or generated by a tool. A
   priority-1 rule of this shape shadows every other egress rule.
5. Does the probe hit any other explicit Drop rule?
6. If nothing blocks: report that the cloud side shows no blocking finding, and
   state the group-type caveat. A normal-type group permits outbound by default;
   an enterprise-type group does not. Confirm the type before declaring the
   cloud side clean.

**Ingress:**

1. Does any ingress rule accept the probed protocol and port? Unmatched inbound
   traffic is dropped silently, which produces a timeout and never an immediate
   reset. That distinction is diagnostic.
2. Does the probe hit an explicit Drop rule?
3. Does the instance have a public address or EIP at all? Without one, an
   outside client cannot reach it directly.
4. Is ICMP accepted in any group? If not, a failed ping is expected and proves
   nothing about TCP reachability. Surface this whenever the error class is a
   timeout, because it reverses a frequent misdiagnosis.

**Internal:**

1. Locate the peer instance. If it is not in this region and account, say so:
   cross-region and cross-VPC interconnect design belongs to
   `alibabacloud-network-diagnose`.
2. Are both instances in the same VPC? Different VPCs means plain private
   addresses cannot route between them.
3. Does the peer address fall inside some VSwitch CIDR of the VPC? Outside
   every CIDR means either another network or a guest-side route problem.
4. If the peer address is not private, this is an internet path - re-run with
   `--direction egress`.
5. Does an ingress rule accept the probed port from the peer address or peer
   group?
6. Report the VSwitch CIDR map, and note that per-entry route next-hop detail is
   not exposed by the route table query. The guest-side route and policy-route
   items in the inspection checklist close that gap. With more than one network
   interface, asymmetric return-path routing is a known cause of "can send,
   cannot receive".

## D4 - Target geography

Decide whether the path crosses the Chinese mainland border.

- The instance region classifies as mainland or overseas. Every `cn-` region is
  mainland except `cn-hongkong`; anything else is overseas.
- The target classifies from a customer or operator declaration, or from a
  known-overseas endpoint hint. With neither, the location is `unknown`.

Cross-border is selected when the instance is mainland and the target is
overseas on an egress probe, or the instance is overseas and the client is
mainland on an ingress probe.

When direction is egress, the region is mainland, the target location is
`unknown` and the error class is a timeout, emit a warning instead of an
attribution: resolve the name to a real address, or pass `--target-location`,
before blaming the link. Attributing a timeout to cross-border congestion
without knowing where the target lives is the single easiest wrong answer in
this domain.

Wording, options and hard limits for this branch:
[cross-border-and-blockage.md](intranet-egress__cross-border-and-blockage.md).

## D5 - Guest-side state

No cloud query exposes the host firewall state, the address a service binds to,
guest routes and DNS, proxy configuration, live probe results, or whether a
request arrived in the service log. That evidence only exists inside the
instance.

The only path is manual: print the inspection checklist for the customer to
run and paste back as plain text. Ask for text, not screenshots - text is
interpretable, a screenshot is not.

There is no automatic path: the skill is strictly read-only and never executes
anything inside the instance. `scripts/areas/intranet_egress/guest_command_gate.py` makes no cloud
call; it prints the checklist and validates a proposed inspection command
against the inspection-only text guards before it is handed to the customer.
See [guest-inspection-commands.md](intranet-egress__guest-inspection-commands.md).

The most valuable single item in this step is **request arrival**: if the
customer's request appears in the web or application log, the packet reached the
instance and the fault sits above the network layer. That one observation ends
more investigations than any rule read-back.

## D6 - Attribution and next step

| `ATTRIBUTION` | Set when | Next step owner |
| --- | --- | --- |
| `cloud-config` | Any blocking cloud-side finding from D3 | Resource owner, in the console. This skill never edits configuration. |
| `external-link` | D4 selected the cross-border branch | Customer evaluates options; the cloud controls neither end of the link. |
| `external-carrier` | Ingress plus a reset class, especially single-region multi-carrier | Customer contacts the carrier. |
| `application-layer` | Refused class, or an HTTP status in the error text | Application or web service owner. Out of scope. |
| `guest-config` | Proxy-path class, or cloud side clean and guest evidence outstanding | Customer runs the checklist. |
| `ownership` | D1 found no instance in this account | Owning account, or the customer's own network team. |
| `guest-config-or-external` | Cloud side clean, evidence incomplete | Collect guest evidence, then re-attribute. |
| `undetermined` | Insufficient evidence | Escalate with the evidence bundle. |

Precedence: a blocking cloud-side finding outranks every other branch. A
customer can be crossing a border **and** have a blanket egress drop rule; report
the rule, because it is the thing they can actually fix.

### Platform-side states with no query entry

When direction is ingress, the error class is a timeout, and no cloud-side
finding explains it, add the escalation step: anti-DDoS blackhole or cleaning
status and underlying host incidents have no public query entry point. Escalate
to a support ticket **with** the evidence bundle this report produced. Make no
claim about whether a block is in force - the skill cannot see it.

### Client-side and third-party

When the evidence shows the service answered normally yet the customer still
cannot reach it, the difference is on the client or the third-party platform.
Provide the self-check list - local hosts file, local DNS cache, browser cache,
retry from another network or device, and for third-party verification flows the
verification method and file placement - and stop. The client machine is not
under management here.

## Evidence discipline

- Quote only values that a query actually returned. An empty result is a fact
  worth reporting; an assumed value is not.
- Declare every parameter that was auto-filled or defaulted, including a region
  taken from the located instance.
- When platform-side observation and the customer's observation disagree, report
  both and say the disagreement is unresolved. Different client addresses take
  different carrier paths, so both can be true.
- A failed query degrades the run; it never silently disappears. Every failure
  lands in the degradation log with its category and code.
