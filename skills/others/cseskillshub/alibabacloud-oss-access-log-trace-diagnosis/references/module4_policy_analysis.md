# Module 4: Bucket-Policy Hit Analysis and Grammar

Two jobs live here: proving **which statement** denied a request, and never
handing the customer a policy example that cannot work.

---

## 1. Evaluation order

Authorization is evaluated in this order, and the order decides the conclusion:

1. An explicit **Deny** that covers the request → denied. Nothing else matters.
2. Otherwise an explicit **Allow** that covers the request → permitted by this
   layer.
3. Otherwise → **implicitly denied**, because there is no Allow.

A statement covers the request only when **all three** of these hold: its Action
covers the logged operation, its Resource covers the bucket and object, and its
Principal covers the caller. Conditions are evaluated afterwards and can turn a
covering statement into a non-matching one.

Corollaries that must be stated to the customer when relevant:

- An explicit Deny outranks every Allow, **including an Allow in a RAM identity
  policy**. Widening a bucket policy cannot undo a Deny.
- A presigned URL does **not** bypass a bucket policy: the policy is evaluated
  before the signature is accepted.
- Block public access overrides both the bucket ACL and the object ACL.

---

## 2. Bucket policy versus RAM policy — never mix the grammars

| | Bucket policy | RAM policy |
|---|---|---|
| Attached to | The bucket | A RAM user, group or role |
| `Principal` | **Required.** Plain UID strings, an assumed-role ARN, or `*` | **Absent** — the attachment target decides |
| `Resource` | `acs:oss:*:*:<bucket>` or `acs:oss:*:*:<bucket>/*` — **no account number** | `acs:oss:<region>:<uid>:<bucket>/<object>` — includes the account number |
| Source-IP condition | Must be paired with a source-VPC condition | May be used alone |

Writing a RAM-style `Principal` into a bucket policy is the most common
copy-paste failure and it silently authorises nobody.

---

## 3. Principal — the four valid forms

| Authorise | Write |
|---|---|
| An account, or a RAM user under it | `["1234567890"]` — the plain UID as a string |
| An assumed role session | `["arn:sts::<ownerUid>:assumed-role/<roleName>/*"]` |
| Everyone, including anonymous | `["*"]` |
| Several of the above | List them all in one array |

### Four ways this goes wrong

1. **Object form.** `{"RAM": ["acs:ram::1234567890:root"]}` is RAM-policy syntax.
   In a bucket policy it matches nothing.
2. **`role/` instead of `assumed-role/`.** `arn:sts::<uid>:role/<name>` is not a
   valid principal for a role session.
3. **A hardcoded session name.** `arn:sts::<uid>:assumed-role/<name>/my-session` only
   matches that exact session. Services that assume a role generate a fresh
   session name per request, so the statement stops matching immediately. Use
   `/*`.
4. **A bare UID for a role session.** A UID principal matches the account and its
   RAM users making direct requests; it does **not** match an assumed-role
   session. Both forms are needed when both paths exist.

The session-name trap is a frequent real cause: a customer grants the account
that owns a role, while the actual requests arrive as assumed-role sessions with
dynamic session names generated by a compute service.

---

## 4. Resource

```
acs:oss:*:*:example-bucket          # the bucket itself: listing, bucket config
acs:oss:*:*:example-bucket/*        # every object in the bucket
acs:oss:*:*:example-bucket/images/* # one prefix
```

No account number appears in a bucket-policy resource. Listing operations target
the bucket resource, object operations target the object resource — granting only
one of the two is why "I can upload but cannot list" happens.

---

## 5. Condition keys — whitelist only

Only these keys are supported. Anything else must be reported as unsupported;
inventing a plausible key produces a policy that silently does nothing.

| Key | Meaning |
|---|---|
| `acs:SourceIp` | Source IP. In a bucket policy it must be paired with `acs:SourceVpc` |
| `acs:SourceVpc` | VPC ID |
| `acs:UserAgent` | User-Agent header |
| `acs:AccessId` | AccessKey ID; a temporary-credential prefix pattern matches temporary credentials |
| `oss:Prefix` | Object prefix — **listing APIs only**, see below |
| `oss:Delimiter` | Delimiter — listing APIs only |
| `oss:ExistingObjectTag/<key>` | An existing object tag |
| `oss:BucketTag/<key>` | A bucket tag |
| `oss:x-oss-acl` | Bucket ACL |
| `oss:x-oss-object-acl` | Object ACL |
| `oss:object-remaining-retention-days` | Retention days remaining under a retention policy |
| `oss:ClassicIntranet` | Classic-network access flag |

### Requests that cannot be expressed as a condition

| Requested | Reality | What to do instead |
|---|---|---|
| Restrict by Referer | Neither an `acs:` nor an `oss:` referer key is supported | Configure the bucket's hotlink-protection whitelist, which is a separate bucket setting |
| Restrict the upload content type | Not supported by bucket policies or RAM policies | Use a form-upload policy, or a presigned URL that fixes the content type |

When a key is not supported, say so plainly. Do not offer a nearby-looking key.

### `oss:Prefix` restricts listing, nothing else

The prefix condition only applies to APIs that carry a prefix parameter, which
means listing operations. An object read or an object write has no prefix
parameter, so the condition never matches and the statement restricts nothing.

To restrict by key pattern on reads and writes, use the **Resource** element with
a wildcard (`acs:oss:*:*:example-bucket/*.html`), not a prefix condition.

---

## 6. Operators and wildcards

| Operator | Honours `*` |
|---|---|
| `StringLike` / `StringNotLike` | **Yes** |
| `StringEquals` / `StringNotEquals` | **No** |
| `IpAddress` / `NotIpAddress` | No — takes addresses and CIDR ranges |
| `Bool` | No |

Using `StringEquals` with `["*"]` is a silent configuration bug: the asterisk is
compared as a literal character, so the condition never matches any real VPC ID.
The engine flags this as a configuration bug whenever it evaluates such a
statement.

---

## 7. Restricting by source IP — the pairing rule

A source-IP condition in a bucket policy **must** be accompanied by a source-VPC
condition. The reason: an IP condition alone does not distinguish the public
network from a VPC, so the same address range inside someone else's VPC also
matches — an over-permissive result that looks correct.

### Public-network allowlist (VPC condition made always-true)

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": ["1234567890"],
      "Action": ["oss:GetObject"],
      "Resource": ["acs:oss:*:*:example-bucket/*"],
      "Condition": {
        "StringLike": { "acs:SourceVpc": ["*"] },
        "IpAddress":  { "acs:SourceIp": ["203.0.113.0/24"] }
      }
    }
  ]
}
```

`StringLike` with `["*"]` matches any VPC value **and** a request that carries no
VPC attribute at all, which is exactly what a public-network request looks like.
`StringEquals` with `["*"]` would not.

### One specific VPC plus an IP range

```json
"Condition": {
  "StringEquals": { "acs:SourceVpc": ["vpc-bp1exampleexample"] },
  "IpAddress":    { "acs:SourceIp": ["192.168.1.0/24"] }
}
```

Here the exact operator is correct, because a concrete VPC ID is being matched.

## 8. Working a denial: the method

Inputs: the policy document, and one traced log row.

| Condition key | Logged field it is evaluated against |
|---|---|
| `acs:SourceIp` | `client_ip` |
| `acs:SourceVpc` | `vpc_id` (empty or `-` means a public-network request) |
| `acs:AccessId` | `access_id` |
| `acs:UserAgent` | `user_agent` |
| `oss:Prefix` | the prefix parameter inside `request_uri` |

Steps:

1. Read the policy. A 404 on the read means **no policy exists** — that is a
   finding, not a failure, and it rules this whole family out.
2. For each statement, decide whether Action, Resource and Principal all cover
   the request.
3. For covering statements, evaluate each condition against the logged values.
4. Apply the evaluation order from section 1.
5. Report the matched statement **verbatim**, plus a per-condition table showing
   expected value, actual value, and whether it was met.

A condition that cannot be evaluated from the log is reported as "not evaluable"
with the reason. It is never reported as met, and never as unmet.

### Output shape

```
Statement #2 (Effect: Deny) applies:
  Action covers the logged operation 'GetObject': yes
  Resource covers 'example-bucket/images/a.png': yes
  Principal: Principal ["*"] covers every caller, including anonymous
  Condition NotIpAddress acs:SourceIp: expected ['203.0.113.0/24'],
            actual '198.51.100.7' -> MET
  Condition StringNotLike acs:SourceVpc: expected ['vpc-*'], actual '-' -> MET
  Every required condition is satisfied, so the Deny takes effect.
```

Quote the statement itself, not a paraphrase of it. The customer must be able to
check the reasoning against their own configuration.

## 9. Deciding whether a request is cross-account

A RAM user's identifier always differs from the account number, so **a bare
inequality proves nothing**. Use the right field for the request type:

| Request type | How to recognise it | Compare this with the bucket owner |
|---|---|---|
| Anonymous | `sign_type: NotSign`, `access_id: -` | Nothing to compare; the request has no identity |
| Account or RAM user, direct | `extend_information` empty or `-` | `requester_id` — but a difference only means "a RAM identity", not "another account" |
| Assumed role | `extend_information` populated | `roleOwnerId`, the **fourth** field |

`extend_information` layout, comma separated:

```
requesterParentId , roleName , roleSessionName , roleOwnerId
```

Further fields may be appended by later versions, so index from the left and
tolerate extra fields.

Example: `1111222233334444,ExampleRole,session-0a1b2c3d,5555666677778888`
means the role `ExampleRole` belongs to account `5555666677778888` and was
assumed by account `1111222233334444`. Whether this is cross-account access is
decided by comparing `5555666677778888` with the bucket owner — not the first
field.

## 10. Fixes to propose, and their exact wording

| Finding | Proposal |
|---|---|
| A Deny matched on source IP | Add the real egress address to the allowlist, or issue the request from the permitted VPC, or use temporary credentials if the Deny exempts them |
| A Deny matched on source VPC | Issue the request from inside the permitted VPC; a public-network request never carries a VPC attribute |
| No Allow covers the request | Add an Allow statement; use the assumed-role ARN form with `/*` when the caller is a role |
| Anonymous listing denied on a public bucket | Add an Allow with principal `*` and the listing action on the bucket resource |
| `StringEquals` with a wildcard | Change the operator to `StringLike` |
| Source-IP condition used alone | Add a source-VPC condition, `StringLike` with `["*"]` for a public-network allowlist |
| Prefix condition used to restrict reads or writes | Move the restriction into the Resource element with a wildcard |
| Referer restriction attempted via a condition | Configure the hotlink-protection whitelist instead |
| Explicit Deny in a RAM identity policy | Narrow or remove that Deny; a bucket-policy Allow cannot override it |

Every proposal is guidance only. This skill is read-only and never applies a
policy change, even when the customer asks it to "just fix it".
