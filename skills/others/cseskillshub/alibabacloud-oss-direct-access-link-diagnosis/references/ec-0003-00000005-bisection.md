# EC 0003-00000005 Attribution SOP (Object-Level Read Denial)

Attribution SOP for the OSS error code `0003-00000005`
(server-log ErrorMsg: `You do not have read permission on this
object.` — measured 2026-09-03; the official page gives the Chinese
description only, no English ErrorMsg text — H-1):
a GET/HEAD on ONE object returns 403 although the bucket ACL is
public-read / public-read-write, OR the caller's credentials are
rejected. The diagnosis entry runs this attribution automatically
whenever the `--object` probe returns 403 on a non-private bucket,
and reports the outcome as `probe.analysis`.

**Official source**: help.aliyun.com/zh/oss/user-guide/0003-00000005
(B-12 fix, 2026-09-03 — rewritten to match the official 3-cause
structure; the previous "exactly two documented causes" claim was
contradicted by the official page).

## 1. Official problem description and causes

Official "Problem description" (the official page is Chinese-only; the
English below is a faithful translation):
> You do not have read permission on the Object you are accessing, **or the
> credentials you provided are incorrect**.

Official "Problem causes" (two parallel entries):
> * You issued a read request on an Object but do not have read permission on
>   that Object.
> * **The account AccessKey ID or signature you provided is incorrect, causing
>   authentication to fail.**

Official "Problem examples" (two paragraphs):
> For example, you accessed an Object anonymously but that Object's ACL is set
> to private; or you accessed an Object through some account, but the Bucket
> the Object belongs to does not belong to the account you are using, and that
> Object's ACL is set to private.
>
> For example, although your Bucket or Object is set to public-read or
> public-read-write, **the Bucket has the "Block Public Access" feature
> enabled, which also causes the request to be denied**.

## 2. Attribution order: precondition + 3 official causes

Check in this fixed order. Do NOT skip a cause or invent causes beyond
the official list.

| Step | Candidate cause | Check | Outcome |
|---|---|---|---|
| 0 (precondition) | Referer hotlink rules deny the request | bucket referer config (GetBucketReferer) | `referer_denied_403` — attributed BEFORE the EC causes; fix per referer-rules.md |
| 0b (precondition) | Block Public Access overrides public-read | bucket/account Block Public Access switch | `block_public_access_403` — official "Problem examples" paragraph 2; the switch denies anonymous GET even when ACL is public-read |
| 1 | **Cause-1**: the object carries its OWN `private` ACL (bucket is public-read / public-read-write) | read the object ACL via `oss:GetObjectAcl` (script does this automatically) | ACL == `private` -> `object_acl_private_403`, root cause confirmed |
| 2 | **Cause-2**: AccessKey ID or signature incorrect → authentication failure (official "Problem causes" entry 2) | request carries an Authorization header; AK ID / signature / RAM / STS permission is wrong | `auth_failure_403` — the 403 is an authentication/authorization error, NOT an anonymous-access issue; verify AK ID, signature, RAM policy, STS token expiry |
| 3 | **Cause-3**: no remaining official cause applies; escalate | only after causes 1–2 are excluded | `unattributed_403` — boundary statement (section 4); no official cause remains; escalate to the violation-handling channel or the sibling security-incident-forensics skill |

> **Anti-pattern (B-12 fix)**: the previous version of this SOP claimed
> "EXACTLY two documented root causes" and listed "platform-level block"
> as Cause-2. The official page documents THREE cause families (no read
> permission / AK-or-signature incorrect / Block Public Access overriding
> public-read) and contains NO mention of "platform-level block",
> "content-security system interception", or "cloud-shield interception".
> Those terms are NOT official causes of this EC and MUST NOT be presented
> as such. The former `platform_block_suspected` verdict is replaced by
> `unattributed_403` with an explicit D-class boundary statement.

## 3. Cause-1: object-level private ACL

**Verification (automatic)**: the script calls `GetObjectAcl`
(`oss:GetObjectAcl`, read-only) on the probed object and attaches the
raw grant to `probe.analysis.object_acl`. Manual equivalent for the
user:

```bash
ossutil ls oss://<BUCKET>/<OBJECT_KEY> --acl -e oss-cn-<REGION>.aliyuncs.com
```

**Fix template (manual operation — this skill never applies it)**:
restore the object to inherit the bucket ACL:

```bash
ossutil set-acl oss://<BUCKET>/<OBJECT_KEY> default -e oss-cn-<REGION>.aliyuncs.com
```

For a batch problem (many objects under the same bucket carry their
own private ACLs), the recursive form:

```bash
ossutil set-acl oss://<BUCKET>/ default -r -e oss-cn-<REGION>.aliyuncs.com
```

> ossutil must resolve credentials from its own default chain
> (environment variables / its config file). NEVER pass AK/SK on the
> command line.

## 4. Cause-2: authentication failure (AK ID / signature / RAM / STS)

Official "Problem causes" entry 2 (translated): "The account AccessKey ID or
signature you provided is incorrect, causing authentication to fail."
Official "Solutions" entry 1 (translated): "Make sure the account AccessKey
ID you provided is correct and the AccessKey Secret used for the signature is
correct."

This cause applies when the request carries an `Authorization` header
(signed API/SDK call) and the 403 is an authentication or authorization
failure — NOT an anonymous-access issue. Common sub-cases:

- AK ID is wrong or belongs to a different account.
- Signature computation error (wrong SK, wrong string-to-sign, clock skew).
- RAM user / STS token lacks `oss:GetObject` on the target resource.
- STS token has expired.

**Fix template (manual guidance)**:
1. Verify the AK ID and SK are correct and belong to the intended account.
2. If using RAM user or STS, verify the policy grants `oss:GetObject` on
   `acs:oss:*:*:<bucket>/<key>`.
3. If using STS, check the token expiry (`Expiration` field).
4. For signature errors, verify the string-to-sign construction and clock
   synchronization.
5. Defer to sibling skills: alibabacloud-oss-cross-account-auth-diagnosis
   (cross-account), alibabacloud-oss-presigned-url-v4-diagnosis (presigned
   URL / V4 signing).

## 5. Cause-3 / unattributed: boundary statement and escalation

Consider ONLY after causes 1–2 and the preconditions (referer, Block
Public Access) are all excluded. No official cause remains.

Boundary statement: the official EC 0003-00000005 page documents three
cause families (sections 2–4 above). When none applies, this skill
CANNOT attribute the 403 to a specific official cause. It defers:

1. Escalate through the violation-handling channel (ticket / compliance
   appeal) — the platform's violation-handling team can check internal
   block records that have no public query interface.
2. For traffic-theft or leaked-credential-abuse context, defer to the
   sibling alibabacloud-oss-security-incident-forensics skill.

> **D-class note (internal observation, NOT official)**: historically an
> earlier internal knowledge asset attributed unexplained 403s on public-read buckets to a
> "platform-level block". The official EC page contains no such cause.
> This SOP retains the escalation path but labels it `unattributed_403`
> rather than asserting an unofficial cause. (measured 2026-09-03:
> the original Chinese official page was grepped for platform-ban /
> content-security / cloud-shield terms = 0 hits.)

## 6. Script verdict mapping

| `probe.analysis.verdict` | Meaning |
|---|---|
| `referer_denied_403` | referer rules deny the probe (blacklist hit / whitelist miss / empty-referer denial with non-empty whitelist) — attributed BEFORE the EC causes |
| `block_public_access_403` | Block Public Access switch overrides public-read and denies anonymous GET (official "Problem examples" paragraph 2) — precondition, not an EC cause |
| `object_acl_private_403` | Cause-1 confirmed: GetObjectAcl returned `private`; fix per section 3 |
| `auth_failure_403` | Cause-2: the request carries an Authorization header and the AK ID / signature / RAM / STS permission is incorrect (official "Problem causes" entry 2); fix per section 4 |
| `unattributed_403` | Causes 1–2 and preconditions excluded; no official cause remains — boundary statement + escalation per section 5 |
| `object_acl_unverifiable` | GetObjectAcl degraded on a public-read bucket -> Cause-1 leading hypothesis per the inference rule; have the owner verify manually |
| `http_error` | probe transport error — retry / check network; no attribution is attempted |
