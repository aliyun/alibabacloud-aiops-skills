# OSS Presigned-URL Advisory FAQ

Embedded knowledge distilled from real presigned-URL advisory (first-question)
support tickets. These entries answer consult-style questions ("is this
safe?", "which option should I pick?", "where do I configure it?"); error
reports are routed by the failure catalog in
`presigned-url-failure-catalog.md` instead. The entry script lists this file
in its `references` output for every routed diagnosis, so the Agent consults
it whenever the customer wording is advisory rather than an error report.

Answers are knowledge constants verified against official documentation and
support-ticket conclusions (verification date 2026-09-02); account-specific
numbers must never be added from memory.

## 1. Is a presigned URL carrying OSSAccessKeyId insecure? (ticket 000EAR5FN7)

Customer original wording (translated from Chinese): the link generated by
the SDK `sign_url` function carries the `OSSAccessKeyId` parameter; an
external assessment agency says this is insecure — how do I rebut that?

Support-verified answer:

- **`sign_url` is the official, standard and secure design.** Carrying
  `OSSAccessKeyId` and `Signature` in the URL query is exactly how URL-signed
  requests are specified in the official documentation
  (https://help.aliyun.com/zh/oss/developer-reference/include-signature-in-url,
  verified 2026-09-02).
- The assessment **confused the AccessKeyId of a time-limited signed URL
  with a long-term AK/SK pair**. The URL exposes the key id (an identifier)
  plus a signature that is bound to the signed resource, method and expiry
  window; it does not expose the SecretKey, so possessing the URL does not
  enable forging other requests.
- **STS temporary credentials are the better practice where applicable**
  (least privilege, automatic expiry), but that does not make `sign_url`
  insecure — both are supported official mechanisms.

## 2. Bucket switched to private broke all stock links — go back to public-read with hotlink protection, or stay private and re-sign? (ticket 000ACR8SY2)

Customer original wording (translated from Chinese): after the bucket went
private, all the old links stopped working — is it better to switch back
to public-read with hotlink protection, or keep private and regenerate
signed links?

Support-verified answer (business trade-off for protecting stock links):

- After the bucket goes private, the old bare links **cannot be accessed any
  more; signed information must be appended** to every link (presigned URL or
  CDN URL auth). No switch keeps old bare links working on a private bucket.
- When the pain is a large stock of already-published bare links, the
  support-recommended path is: **keep the current public-read posture and add
  hotlink protection (Referer allow-list) instead of flipping to private**
  (official doc: https://help.aliyun.com/zh/oss/user-guide/hotlink-protection,
  verified 2026-09-02; black-list rules take precedence over white-list
  rules, wildcards `*` and `?` are supported).
- When the objects are genuinely sensitive, stay private and regenerate
  signed links — the `long_term_private_access` guidance in
  `presigned-url-failure-catalog.md` covers on-demand re-signing with short
  TTL, CDN private back-to-origin with URL auth, and RAM/STS programmatic
  access.
- Decision rule of thumb: **sensitive content → private + signing; public
  content with anti-leech needs → public-read + Referer rules**. Avoid
  flipping the ACL back and forth: each flip invalidates one whole class of
  links.
- The traffic-abuse perspective of the same trade-off (scraping, referer
  bypass, emergency containment) lives in
  `../alibabacloud-oss-security-incident-forensics/references/traffic-abuse-playbook.md`;
  consult it when the customer reports actual traffic abuse rather than a
  link-management question.

## 3. Custom-domain SSL certificate expired — where do I renew it? (ticket 0001ZRG446)

Customer original wording (translated from Chinese): my domain's SSL
certificate has already been renewed, but when downloading through the
file-oss domain the server reports the SSL certificate has expired — do I
need to configure something in OSS?

Support-verified answer:

- Where the certificate must be renewed depends on **where the domain
  resolves** (official doc: https://help.aliyun.com/zh/oss/user-guide/access-oss-by-https-protocol,
  verified 2026-09-02):
  - Domain resolving to OSS (bucket endpoint): the SSL certificate must be
    hosted on the OSS side — see the `custom_domain_presigned` mode in
    `presigned-url-failure-catalog.md`.
  - Domain resolving to CDN: the certificate is updated in the **CDN
    console, not in OSS** — renewing it on the origin (OSS) side does not
    fix what the edge serves.
- For full CDN back-to-origin diagnosis (origin auth mode, private-bucket
  back-to-origin, edge certificate configuration), hand off to
  `alibabacloud-oss-cdn-origin-config-diagnosis`.
