# OSS Quota & Throttling Rules (Official Defaults)

The quota context this skill reports comes from the official documentation
(fetched 2026-08-27). These are the SYSTEM DEFAULT LIMITS, not measured
utilization: OSS exposes no public API to query the actual bandwidth/QPS
watermark of an account or bucket.

**Verification boundary (public vs internal).** What this skill CAN verify
from public channels: the official per-region bandwidth/QPS default limits,
the thresholds at which throttling fires, `x-oss-qos-delay-time` semantics,
the 503/429 error-code table, and the quota-increase / resource-pool process
wording - every figure below is doc-verified against the official limits
pages. What NO public OSS API exposes (internal channel / console / ticket
only): (1) the account's or bucket's REAL bandwidth/QPS utilization watermark
(the actual Gbps-level water level); (2) real throttling-event records; (3)
the approval status or decision of a quota-increase / dedicated-bandwidth
request. Never attempt to query these three through any public API inside the
sandbox and never fabricate them - report the official defaults as context and
direct the user to console Usage Query > Basic Data / CloudMonitor (for
utilization) or the ticket channel (for approval status).

## 1. Bandwidth defaults (per account, per region)

Unit: Gbps. "Total" = internal + public combined.

| Region | Total download | Public download | Total upload | Public upload |
|---|---|---|---|---|
| cn-hangzhou (East China 1) | 100 | 20 | 20 | 20 |
| cn-shanghai (East China 2) | 100 | 10 | 20 | 10 |
| cn-shenzhen (South China 1) | 100 | 10 | 20 | 10 |
| cn-beijing (North China 2) | 100 | 10 | 20 | 10 |
| ap-southeast-1 (Singapore) | 100 | 5 | 20 | 5 |
| cn-zhangjiakou (North China 3) | 20 | no separate cap | 20 | no separate cap |
| cn-nanjing (East China 5) / cn-fuzhou (East China 6) - local regions, **official status: being shut down / decommissioning** | 2 | no separate cap | 2 | no separate cap |
| cn-wuhan-lr (Central China 1, local region) / ap-northeast-2 (Seoul) / ap-southeast-7 (Bangkok) | 2 | no separate cap | 2 | no separate cap |
| Other mainland regions | 10 | no separate cap | 10 | no separate cap |
| Other non-mainland regions | 5 | no separate cap | 5 | no separate cap |
| No-region-attribute buckets | 10 | no separate cap | 10 | no separate cap |

> Region-status note (verified 2026-09-03, official limits doc): the 2 Gbps
> figure for cn-nanjing / cn-fuzhou is correct, but the official limits table
> marks both as "local region - being shut down" (decommissioning). When a user
> asks about throttling/capacity in these two regions, surface the shutdown
> status and advise planning a migration to another region rather than
> scaling up there. cn-wuhan-lr is also a local region but is NOT marked as
> shutting down; ap-northeast-2 (Seoul) and ap-southeast-7 (Bangkok) are
> normal regions.

When a threshold is reached, requests are throttled. Throttled responses
carry the response header `x-oss-qos-delay-time: <ms>` - upload requests
get the precise delay, download requests an estimate based on throttling
degree and object size.

Counting scope (official limits doc): requests generated by OSS background
system tasks (lifecycle rules, cross-region replication, same-region
replication, access-time updates) do NOT count against the account
QPS/bandwidth quota; cross-region replication has an independent QPS
budget. Operations issued with STS temporary credentials obtained via
AssumeRole DO count against the quota normally.

## 2. QPS defaults (per account)

| Access pattern | QPS |
|---|---|
| Non-sequential reads/writes | 10,000 |
| Sequential-prefix reads/writes | 2,000 |

- Single-object upload/download total QPS caps at 2,000 with a peak
  bandwidth of 10 Gbps (also bound by the region and bucket limits).
- Even when the account-wide QPS stays below the threshold, requests
  concentrated on one partition can be throttled at the per-partition
  service capacity; well-dispersed prefixes let OSS scale partitions
  automatically.
- QPS limit increases are NOT self-service via the quota center - submit
  a ticket; engineers evaluate the actual usage before raising it.
- Mirror back-to-origin has its own budget, separate from the account QPS:
  default 2,000 QPS / 2 Gbps per region in mainland regions (and
  HK per the limits doc), 1,000 QPS / 1 Gbps in overseas regions; over-limit
  requests fail with EC `0041-00000102` and raises need a ticket.

## 3. Throttling error-code table (503 + 429 family)

| Error code | HTTP | Server message | Meaning | Direction |
|---|---|---|---|---|
| DownloadTrafficRateLimitExceeded | 503 | Please reduce your download request traffic | Download bandwidth exceeded the limit | download |
| UploadTrafficRateLimitExceeded | 503 | Please reduce your upload request traffic | Upload bandwidth exceeded the limit | upload |
| TotalQpsLimitExceeded | 503 | Max total qps limit is exceeded | Account total QPS exceeded the limit | both |
| MetaOperationQpsLimitExceeded | 503 | Qps limit for the meta operation is exceeded | Management-plane API QPS exceeded: GetService (ListBuckets); bucket ops such as PutBucket/GetBucketLifecycle; CORS ops such as PutBucketCORS/GetBucketCORS; LiveChannel ops such as PutLiveChannel/DeleteLiveChannel. Retry after a few seconds | both |
| ActiveRequestLimitExceeded | 503 | Max active request limit is exceeded | Concurrent active requests exceeded the limit | both |
| CpuLimitExceeded | 503 | Please reduce your request rate | Image-processing concurrency exceeded the CPU cap | both |
| ServiceUnavailable | 503 | Thread pool is almost full, please retry later | OSS server busy; retry later | both |
| PartitionQpsLimitted | 503 | (503 body) | Hotspot partition: requests concentrated on sequential prefixes at one moment trigger per-partition throttling (EC `0026-00000028`); fix by dispersing key prefixes | both |
| QpsLimitExceeded | 429 | Please reduce your request rate | Request rate exceeded the server-side rate limit over a period; lower the request rate and retry | both |

"SlowDown" is the generic 503 throttling marker customers report; treat it
as the throttle family and correlate with the watermark evidence.

Throttling impact differs by type (official): BANDWIDTH throttling raises
access latency; QPS throttling drops/rejects part of the requests with 503.

## 3a. Throttling system events (CloudMonitor alarm names)

OSS emits user-level and bucket-level bandwidth/QPS throttling system
events; configure CloudMonitor event alarms to get notified proactively.

- Naming: `{Bucket|User}{Egress|Ingress}Bandwidth` / `{Bucket|User}Qps`
  are INFO "reporting threshold" events; the matching
  `...ThresholdExceeded` names are WARN throttling events. Bandwidth WARN
  = latency increase; QPS WARN = some requests dropped/rejected (503).
- Mirror back-to-origin: `BucketMirrorIngressBandwidthThresholdExceeded`,
  `BucketMirrorQpsThresholdExceeded`, and their `User...` variants.
- Image processing CPU: `BucketImageCpuThresholdExceeded` /
  `UserImageCpuThresholdExceeded`.
- Reporting threshold = throttling threshold x 0.8 (official).
- Alarm cadence: throttling alarms fire once per minute when throttling
  lasted >= 30 s within the minute; reporting alarms once per 10 minutes
  when the threshold was hit for >= 1 s.
- Event JSON `content` fields: `TargetRate` (throttling threshold,
  bytes/s), `TrafficRate` (current rate, INFO events), `AvgSeverity`
  (throttling degree 0-100, WARN events), `QoSType`
  (EgressBandwidth/IngressBandwidth/...), `TrafficSource`
  (intranet/extranet/net_all).

## 4. Watermark verification channels (no public query API)

1. OSS console: bucket -> Usage Query > Basic Data (bandwidth/QPS trends).
2. CloudMonitor OSS metrics for the account/bucket in the region.
3. The `x-oss-qos-delay-time` header on throttled responses.
4. OSS log delivery / real-time log query to inspect source IP / UA /
   referer concentration when traffic grows unexpectedly.

OSS has no SERVER-SIDE user-defined rate limiting (no console or API entry
to throttle others); per-client frequency control must be implemented with
WAF or ESA instead. Note the distinct client-side tool: single-connection
bandwidth throttling via the `x-oss-traffic-limit` request parameter
(819,200~838,860,800 bit/s), supported on PutObject / AppendObject /
PostObject / CopyObject / UploadPart / UploadPartCopy / GetObject - this
limits the CALLER's own connection bandwidth (e.g. to protect other apps on
the same host); it is NOT a server throttle and cannot limit other clients.

## 5. Attribution rule of thumb (ticket-proven)

- Throttle-family error code captured -> server-side throttling confirmed.
- Measured peak above the table limit -> quota pressure, even without a
  captured code.
- Timeouts with zero server-side 5xx and no throttle codes -> client-side
  or network path first (DNS, cross-region/cross-border links, client
  bandwidth); confirm with access logs before mentioning throttling.
- Quota granularity is NOT bucket-only: limits also apply at the account /
  billing-dimension level. Ticket-proven cases show billing-dimension
  bandwidth throttling (e.g. capped at 5 Gbps) and user-level bandwidth
  caps (e.g. 40 Gbps) being hit while any single bucket looked idle - when
  several buckets throttle at once, attribute to the account/billing level
  first (ticket evidence: oss07 00021RB9TD, 00021RGWXD).
