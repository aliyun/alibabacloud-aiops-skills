# Private-Bucket Back-to-Origin Authorization Playbook

When the CDN origin is a **private** OSS bucket, CDN back-to-origin requests
are anonymous reads from OSS's point of view: OSS returns **403
AccessDenied** unless an explicit authorization lets the CDN service read
the bucket. This playbook lists the three supported authorization methods.
They are **manual guidance only** — this skill never enables or modifies any
of them.

> Observability limit (MANDATORY): this skill can prove the bucket is
> private and who owns it (GetBucketInfo: `acl`, `owner_id`), but it
> **cannot read whether an authorization is already enabled**. Always phrase
> the conclusion as "back-to-origin returns 403 unless the authorization is
> in place — verify it", never as "the authorization is missing" (a fact
> this skill cannot establish).

## Method 1 — Private-bucket back-to-origin authorization (CDN console, STS-based)

The recommended same-account path. In the CDN console, the origin settings
of the domain offer the private-bucket authorization switch. Enabling it
lets the CDN service assume the service role and generate temporary STS
credentials to read the private bucket on back-to-origin.

- Where: CDN console -> domain management -> origin configuration of the
  accelerated domain -> private bucket back-to-origin authorization.
- Prerequisite: the accelerated domain and the bucket belong to the same
  account, and the account allows the CDN service role to access OSS.
- Mechanism (official, grant-alibaba-cloud-cdn-access-permissions-on-private-
  oss-buckets): once enabled, CDN automatically adds an `Authorization`
  header to every back-to-origin request, signed from the authorized
  identity (STS temporary token or AccessKey); OSS authenticates against it.
- Verify afterwards: request a cached URL through the accelerated domain and
  confirm the origin no longer returns 403.

**Signature-parameter conflict (403 even with authorization enabled)** —
official rule: a single request must NOT carry a signature in BOTH the
header and the URL. After private-bucket back-to-origin authorization is
enabled (header signature), any presigned URL parameters on the request URL
(`Expires`, `OSSAccessKeyId`, `Signature`, or V4 `x-oss-signature*`)
conflict with it and OSS returns 403. When the symptom is "authorization is
on but still 403", check whether the URL generated by the client / upstream
is presigned — strip the signature parameters or serve unsigned URLs through
the accelerated domain (cross-check with
alibabacloud-oss-presigned-url-v4-diagnosis when the URL itself is the
question).

**Static-website-hosting conflict** — official rule: this feature conflicts
with the OSS static-website-hosting DEFAULT-HOMEPAGE setting. A private
bucket with static website hosting enabled plus private-bucket back-to-origin
produces `forbidden to list buckets` style errors on back-to-origin; the
official workaround (back-to-origin-troubleshooting) is to disable static
website hosting or stop relying on the default homepage for the CDN origin
path.

**KMS-encrypted buckets** — official rule: if the origin bucket uses KMS
encryption, back-to-origin fails with `forbidden by kms` unless the CDN
service role (`AliyunCDNAccessingPrivateOSSRole`) is granted the KMS
decrypt permission for the bucket's CMK (back-to-origin-troubleshooting).

## Method 2 — Bucket policy (OSS console, grant the CDN service read)

The bucket owner adds a bucket policy on the origin bucket granting the CDN
service (same or cross account) read access to the objects CDN needs.

- Where: OSS console -> bucket -> permission management -> bucket policy
  (Bucket Policy / RAM policy of the bucket).
- Use this when the console switch is unavailable or when fine-grained
  object-prefix scoping is required.
- Cross-account case: the **bucket owner account** must add the policy; the
  CDN-side account alone cannot authorize itself.
- Cross-account ARN formats (official, grant-alibaba-cloud-cdn-access-
  permissions-on-private-oss-buckets, step "authorize another account"):
  - Direct STS authorization -> `arn:sts:uid` where `uid` is the CDN-side
    account ID.
  - AssumeRole -> `arn:sts::{CDN-account-UID}:assumed-role/{role-name}/*`;
    when CDN back-to-originates by assuming a role this exact format is
    MANDATORY — any other form yields 403.

## Method 3 — Origin authentication (back-to-origin authentication rules)

CDN can also be configured to sign back-to-origin requests (back-to-origin
authentication / origin authentication) so the origin validates them. This
is typically used with origin servers that implement their own signature
check; for OSS as the origin, Methods 1/2 are the standard paths. Mention
this method only when the customer's origin is not plain OSS or when their
architecture already relies on back-to-origin authentication.

## Decision table

| Fact measured by this skill | Advice |
|---|---|
| `acl=private`, owner == caller UID | Method 1 first; Method 2 as alternative (PRIVATE_ORIGIN_AUTH_REQUIRED) |
| `acl=private`, owner != caller UID | Cross-account: bucket owner must grant via Method 2, then Method 1 on the CDN side (PRIVATE_ORIGIN_CROSS_ACCOUNT) |
| `acl=public-read` / `public-read-write` | No authorization needed for reads; a 403 then points to origin Host/port or an explicit deny policy (PUBLIC_ORIGIN_NO_AUTH_NEEDED) |
| GetBucketInfo denied (403) for the caller | Treat as cross-account/unreadable origin; advise from the owner side (ORIGIN_BUCKET_NOT_READABLE) |
| Authorization enabled but still 403 | Signature-parameter conflict (presigned URL params + header signature), static-website-hosting conflict, or missing KMS permission for the service role — see the three conflict notes under Method 1 |

## Anti-patterns (do NOT advise)

- Making the bucket public just to fix 403 — security regression.
- Hardcoding any AK/SK into CDN or origin configuration — forbidden.
- Claiming the authorization state without evidence — this skill cannot
  read it; always say "verify".
