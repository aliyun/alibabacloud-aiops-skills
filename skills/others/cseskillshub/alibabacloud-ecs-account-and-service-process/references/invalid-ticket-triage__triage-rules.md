# Triage rules for "test / invalid ticket" (ECS, service-and-process tier)

Tier facts: 36 tickets in the union, one member scenario. This file records the rule
set that `scripts/axes/invalid_ticket_triage/triage_invalid_ticket.py` implements, with the ticket ids behind each
marker. Source-language phrases are kept in the detection table in
`scripts/axes/invalid_ticket_triage/_constants.py` (the marker tuples `EXPLICIT_TEST_MARKERS`,
`AUTOMATED_TEST_MARKERS`, `AUTHORIZATION_MARKERS` and the request patterns); this file
states them in English so the rule set can be reviewed without reading code.

Evidence coverage: 20 of the 36 tickets carried dialogue in the reviewed batch. The
remaining 16 are not covered by these observations, so rule coverage and the false-rate
need a full-data spot check before this table is treated as complete.

## Evidence priority

Customer statement first, read-only cloud facts second, content-pattern inference last.

A cloud API cannot know why a person opened a ticket. An "invalid" verdict is therefore
allowed only when the customer text carries an explicit test or no-action marker
(types A and B) or when the text holds no request structure at all (type C). When
neither holds and the text states something concrete and repeatable (type D), the
ticket is not invalid - even if its title says "test". Suppressing a real request
because of a test label is the costly direction of error: ticket 00094RBRNX was read as
a test and still ended up in "windows instance further processing".

Degradation, stated rather than guessed:

- Read call returns nothing, or credentials cannot see the resource: report "not
  visible to these credentials", never "does not exist". See
  [read-api-usage.md](read-api-usage.md).
- Dialogue missing: judge from title and body only, drop confidence one level, and mark
  the record for review.
- Masked or absent order number, cross-account resource, offline approval progress: name
  it as unavailable and give the exit (ask the customer, or hand to a human).

## Type A - the customer says it is a test

Markers in customer-authored text: an explicit statement that this is a test ticket, a
test of the workflow or a pre-release test, that no handling is needed, that the reader
should ignore it, that it was submitted by misoperation, that it was raised casually,
that it is only for testing, a request to reply and close directly, or "send a file" as
a workflow exercise.

| Evidence | What happened |
|---|---|
| 0008MRUM9Y | "test ticket, no action needed"; agent acknowledged; the ticket was closed by a system event; no follow-up question was asked |
| 000CARUKHA, 000CTRP9CT, 000EARD3C7, 000ETRCM9P, 0003ES5A67, 0006SRXPUE, 000BSRDX6W, 00094RFR1X | title already states test use, ignore-me or no-handling-needed |
| 0004PS8ZX6 | "pre-release test", "test the human-agent path", "send a file"; the first agent message was a transfer-to-human card, then the customer sent filler lines and the flow auto-ended |
| 00085RRETE | agent asked whether it was a ticket test and requested detail or closure; the customer never replied |

Handling in the reviewed tickets was inconsistent: 0003ES5A67 got the answer "1",
00085RRETE got a clarification template, 00021RRMZD got no human handling at all. The
rule set exists to remove that fork: same markers, same verdict, same suggested
disposition, with the evidence listed.

Verdict: `A`, high confidence when the marker is in the title or when more than one
marker matched, medium otherwise. Suggested disposition: archive as a test submission.
Suggested reply: the draft in `REPLIES["A"]`.

## Type B - automated, interface or security test traffic

Markers: an API-test or pop-api label, a canary identifier, cross-account wording,
security verification or penetration wording, "generated by" or automated-test wording,
an end-to-end or regression or load-test label, plus machine-shaped structure in the
body: adjacent brace fragments, a template placeholder with an arithmetic expression,
concatenated numeric runs, JSON key and value shapes, script or substitution syntax, or
an instruction to ignore earlier instructions.

| Evidence | What happened |
|---|---|
| 00021RRMZD | "ai-popapi-test-canary-crossacct" plus an own-reply marker; two machine-authored messages, no human agent turn; the record confirms a controlled cross-account POP API security test |
| 000ACRGR12 | "Test ticket for API testing - ECS usage question" with a concatenated numeric fragment in the first message; the agent answered with the same clarify-or-close template |
| 000FLRREFR | first message carries a malformed brace-and-digit concatenation |
| 000AWRFP3J, 000BSRBSBW | security verification wording; the agent asked in English whether it was a test |

Verdict: `B`. A named automated marker counts as strong evidence; a machine-shaped
pattern alone is enough for `B` only when no explicit test phrase is present, otherwise
the ticket stays in `A` with the payload noted. Suggested disposition: archive as a
controlled test and pass the excerpt to whoever owns security probes - that routing is
not settled in the reviewed evidence (open item), so the report only suggests it.

## Type C - content with no request

Markers: an empty or symbol-only body, an arithmetic or template placeholder, a numeric
or starred filler line, one to three characters in a script-without-spaces language, or
a total customer text under 24 non-space characters, provided no request evidence
matched.

| Evidence | What happened |
|---|---|
| 00085RRETE | body was a placeholder arithmetic string, nothing else |
| 0004PS8ZX6 | masked attachment lines and workflow phrases only |

Verdict: `C`, medium confidence - by construction this verdict depends on the customer
answering. Suggested disposition: one clarification round, then a close suggestion. The
draft matches the wording the agent used in 00085RRETE: confirm whether it is a test,
otherwise describe the problem with instance id, region and the exact message, and
close it if nothing further is needed.

## Type D - a real request wearing a test label

These tickets sit in the union but are not invalid; they are kept as routing samples.

| Evidence | The real request | What the agent did |
|---|---|---|
| 0002HRUTWX | buy a second instance with the same configuration for testing, asks for a discounted price and a monthly option | explained the one-discounted-instance-per-account limit, offered a business manager, then pointed at the product page and the configuration price calculator |
| 000F4RUDD8 | expand the disk of test server i-m5e6pz7ic7zgs08qovrv, asks whether that affects the 5-day no-reason return | said yes it affects it, because expansion is a configuration change, and quoted the unsubscription-rules document |
| 000GJRW460 | shrink or unsubscribe a disk-expansion order submitted by misoperation (masked order number) | said a disk cannot shrink and an upgrade order cannot be unsubscribed alone, and offered the image-rebuild path with an IP change warning |

Verdict: `D`, never `A`. The report classifies the symptom into one of the buckets in
`SYMPTOM_BUCKETS` (purchase and promotion, unsubscribe and refund, disk and order
change, instance fault), states the destination as
[handoff-map.md](handoff-map.md) records it, attaches whatever read-only facts were
confirmed, and supplies the routing reply from `REPLIES["D"]`.

## Cross-cutting risk: "authorized" plus "test"

| Evidence | Combination |
|---|---|
| 00094RBRNX | instance id and "test ticket" in the title, then "operation authorized", then a live processing thread |
| 0003ES5A67, 00094RFR1X, 000BSRDX6W, 000EARD3C7 | test declaration together with "operation authorized" |

Whenever authorization wording appears alongside a test or automated marker, the report
adds `RISK_AUTH`: do not enter the post-authorization operational flow. This skill has no
in-instance or repair capability at all, so the warning protects the next human from an
unnecessary change.

## What automation can and cannot decide

Deterministic from the text: marker vocabulary, machine-shaped payloads, placeholder
content, resource-id presence, authorization-combination risk.

Not available to this skill: the submitter's identity and motive (internal test account
or not), anything in another account or region, the order behind a masked number, the
customer's intent when they never reply, and every ticket-system action. These stay with
a human, and the report lists them under "needed from a human or from the customer".
