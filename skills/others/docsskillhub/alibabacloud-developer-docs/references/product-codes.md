# Product code table: determine product codes and names + fallback when no code is found

This file answers "which product does the user mean, what is it called, what code should the script receive" (`SKILL.md` Step 2). The same product may have different codes in docs, OpenAPI, and CLI — **pass parameters based on live lookup results; never guess from the product name**.

## 1. Full product list: live lookup with `list-products`

The full product list is **not maintained in this file**; the only source is the Help Center navigation menu `mainMenu.json`, fetched live by the script:

    python3 scripts/aliyun_help.py list-products [keyword]                 # China site, Chinese
    python3 scripts/aliyun_help.py list-products [keyword] --site cn -L en  # China site, English
    python3 scripts/aliyun_help.py list-products [keyword] --site intl -L <language>  # International site

- The menu contains `type16` main products and their `type8` / `level4` sub-products. Text columns are **code, categoryId, category4Id, name**: `categoryId` is the main product ID, `category4Id` the sub-product ID (`-` for main products); the short name is in parentheses after the name. `-v` adds the top-level category and a summary. `--json` keeps the original `url` and adds `alias` (semantic path with leading `/`), `node_id`, `node_type`, `category_id` (main product ID), `category4_id` (sub-product ID or `null`), and `parent_code` (the sub-product's main product code; empty for main products). Keywords match product codes, product names, short names, and top-level categories. `-n <N>` only truncates the displayed count (default: all).
- **When the keyword is not a product name** (category/intent words such as the Chinese keywords `发票`, `订单`, `节省计划`, `实名`, or MFA): on no menu match the script runs one same-site full-text search with the same keyword, infers menu products from hit URLs, and emits `WARN[product-from-search]`; in `--json` these rows carry `matched_by: "search"` and `hit_title`. They are candidates only — read the hit bodies to confirm which product the question belongs to. If still exit 1, do not retry with other category words; use the product segment of global `search` result URLs instead.
- **Step 2 determines the "exact product / sub-product" and the "documentation product code (namespace)" separately**: when a keyword hits multiple rows, check the user's object against product names and short names; if mutually exclusive ambiguity remains for the same object (e.g., main vs. sub-product, same name different generations), list candidates (name + code) and ask the user to confirm. Explicit multi-product comparisons, combined usage, or cross-product sub-questions keep all relevant objects; do not force a single choice. A broader doc directory must not rewrite the user's exact product: even though ALB sits under `slb`, quote only ALB-applicable bodies and exclude CLB / NLB conclusions; shared rules must explicitly cover ALB in the body — never auto-apply them just because products share the load-balancing family.
- `code` prefers the official menu semantic `alias` (leading `/` stripped), keeping the legacy code from the menu URL when absent; a doc namespace may hold several sub-products. `list-docs` accepts menu codes or exact legacy `document_detail/<id>.html` / `product/<id>.html` URL codes, then resolves the official alias; the input code is not guaranteed to be used verbatim in catalog requests, and sub-product paths are never guessed. Neither a broad namespace nor `-p` filtering replaces body-applicability verification.
- `search -p <product-code>` automatically filters server-side by menu IDs: known sub-products pass the `categoryId` (main product ID) + `category4Id` (sub-product ID) pair with `topics=DOCUMENT,PRODUCT`; main products pass only `categoryId`. The sub-product URL scope check is defensive only, not the primary classification basis; category-ID auto-discovery is the fallback only when the menu misses. Full-text/index fusion and output caps are not relaxed by alias preference.
- Menus are separate per site and language (China site has only `zh`/`en`; International site has all 7 languages), and the two sites' products differ; **a product missing from one site's menu does not mean it is absent on the other, and one site's conclusion cannot substitute for the other's**.
- The menu cache uses schema 2; old snapshots lacking it are re-fetched, never reused with the old structure. TTL remains 1 day (`~/.cache/alibabacloud-developer-docs/menu/`); when fresh fetch fails, a compatible expired cache may still be used with a stderr `WARN`; when nothing is available, exit code `2`. Expired cache is only a product/path discovery clue, not a currently verified product list or applicability fact; applicable bodies must be re-fetched from the corresponding site. Exit `0` does not prove relevance or list completeness either.
- OpenAPI product codes and versions are looked up separately with `api-products [keyword]`; they are not necessarily the same as doc codes. In `--json`, `versions` is all versions, `defaultVersion` the default, and `recommendVersions` the recommended list (possibly several). Published versions outside the list are not recommended, not deprecated/discontinued; missing or malformed fields mean recommendation unknown, and an empty list means no recommended versions. Never infer recommendation from defaults, version dates, or ordering; version-selection rules are in API lookup rules.
- OpenAPI versions, Endpoints, CLI product names and plugins are **always looked up live**: versions from OpenAPI metadata, endpoints and CLI info from the corresponding official doc bodies. `RegionId` uses the resource's actual owning region; use the `<region-id>` placeholder when unconfirmed — never treat metadata examples or another product's values as the default region.

### First product scoping: menu pre-selection + same-site global cross-validation

When first converging the product scope, you **must additionally run** a same-site search without `-p` beyond the menu query, even if the user named the product explicitly or the menu hit exactly one item. Start with the user's original question (minimally redacted); it may run in parallel with the menu query — a direct RequestId lookup does not wait:

    python3 scripts/aliyun_help.py search "<user's original question, minimally redacted>" -n 5

After the original-wording query, cross-validate with short keywords derived from the goal, capability, symptom, or exact identifiers; keep the original wording, do not substitute rewrites/translations, do not delete the user's own product names, and do not inject extra product names just to lock the pre-selection. Site/language parameters follow `SKILL.md` Step 1; length, language boundaries, and budget are in Doc retrieval rules. Merge and dedupe original and expanded candidates; original-wording hits must enter relevance verification — never look only at rewritten results. Query multiple independent intents separately with short queries as needed; do not concatenate expansion words into long queries; reuse an already-searched original wording.

Compare candidates against the menu pre-selection, read relevant bodies to confirm product identity and whether they answer the user's sub-questions; when products must be added or corrected, look up names and codes live with `list-products` again. Ranking, snippets, shared directories, or passing mentions in a body are not enough to fix the product; when conflicting with the user's explicit object, keep their object, verify the difference, and ask only about ambiguity that affects the conclusion — never substitute silently. No results, errors, or partial results only describe the cross-validation's boundaries; they neither confirm the pre-selection nor exclude other products.

Mutually exclusive candidates for one object need clarification; when multiple products are explicitly involved, keep them all, map products and doc codes per sub-question, gather evidence separately, and verify the linking prerequisites for combined scenarios. List unconfirmed items separately without blocking confirmed independent ones. Do not repeat the global check while the scope is unchanged; redo it when the user changes or adds product scope. The global search does not replace later `search -p` and body verification, and does not authorize cross-site retrieval.

## 2. What to do when a product code finds no body

The script **ships no product-code alias table** (it enumerates neither doc-code spellings like `fc`/`sas`/`alb` nor OpenAPI codes); submitted codes are resolved on the spot by the generic rules below.

**Doc side**: `list-docs` / `search -p` resolve aliases via the official menu, with no hardcoded product mapping; `read-product` still fetches the raw `llms.txt` by the submitted code, not a catalog tree. First distinguish no matching candidates, no usable catalog/index, and retrieval errors. Exit code `1` means no usable results, not uniformly "empty index"; `2` means network/parameter error or currently unverifiable. Partial success keeps stdout records, but warnings mean the results are not exhaustive. Handle in this order; **never guess codes or auto-switch sites**:

1. Look up main/sub-product codes and category IDs live with `list-products <product-name-or-keyword>` for the **confirmed site and language**. Chinese names, English names, and short names all match; trust the returned menu alias, never treat legacy codes or examples as fixed mappings. **Keep the user's exact sub-product**: when only a broader main-product catalog is available, still refine queries and read bodies at the sub-product level; never adopt sibling-product conclusions.
2. `list-docs` prefers the menu alias to fetch and verify the same-site, same-language `menupath.json` subtree. Without a semantic alias, legacy `llms.txt` links only provide candidate doc aliases — the selected node must be verified via `menupath` and the returned root alias adopted; never guess sub-products from arbitrary multi-level paths. Tree-fetch/identity-verification failures warn and fall back to the index with limited scope; an unverified sub-product scope must not be treated as limited. When menu, catalog, and index are all unavailable, locate bodies with same-site `search` using the exact product name, capability words, or candidate official terms, respecting the per-sub-question budget in Doc retrieval rules. `WARN[site-cross]` is only a site-difference notice; it does not authorize automatically retrying on the opposite site. If applicable bodies for the confirmed site still cannot be obtained, state "not found within the scope searched" or "cannot verify at this time". Only a **user-approved cross-site comparison** searches the other site additionally, labeling site, applicability, and source separately; unknowns on the original site remain unknown. Even with no results on both sites, never declare the product (or all products) has no docs.
3. Redirects may keep legacy-code indexes and bodies readable, but **body reads do not return the post-redirect canonical URL**. Before quoting, find the document's actual current link with same-site `search`, then `read` to check title, body identity, and sub-product applicability; never guess new paths or present the original request address as the actual redirect target.

**OpenAPI side** (`api-list` / `api-info`): doc product codes, OpenAPI codes, short names, and Chinese product names are all accepted; `_resolve_meta_product` fuzzy-matches in `products.json` at three tiers, adopting only a unique hit:

1. `code` / `shortName` / `name` **exactly equal** ignoring case and separators (`FC-Open` = `fcopen`; `security-center` hits shortName `Security Center`; the Chinese name `云解析` hits `name`);
2. product name **contains** the submitted keyword (`hologres` → `Hologram`, `dataworks` → `dataworks-public`);
3. short-code **initialism**: the submitted code's letters appear in order in a candidate `code` with the same first letter (`functioncompute` → `FC`).

On multiple hits, stderr lists candidates and asks for the exact `code` (exit code `1`); on zero hits it gives `did you mean` suggestions — then look up live with `api-products <keyword>`.
